## 一、安全风险

### 🔴 S1. 命令注入：插件名未校验直接拼入 shell（plugin-cmds.ts）

**文件**：`packages/cli/src/cli/plugin-cmds.ts:24-28, 61-62, 127, 205-206`

**问题**：`fullName()` 仅做前缀补全，不做任何 shell 元字符过滤。用户输入的插件名直接拼入 `execSync("npm install ${name} ...")` 等 3 处 shell 命令。

```typescript
// 现状：name 可以包含 `; rm -rf /` 或 `$(curl ...)` 等
execSync(`npm install ${name} --prefix "${prefixDir}" --legacy-peer-deps${registryFlag}`, ...);
```

**攻击面**：`plugin install <pkg>`、`plugin uninstall <name>`、`plugin upgrade <name>` 三条命令均可被利用。

**修复建议**：用 npm package name 正则（`/^@?[a-z0-9][\w\-.]*(\/[a-z0-9][\w\-.]*)?$/`）校验 `fullName()` 输入，拒绝含 shell 元字符的输入。

---

### 🟠 S2. 明文密码落盘（auth/store.ts:18-21）

**文件**：`packages/cli/src/auth/store.ts:18-21`

**问题**：`writeCredentials()` 将用户名+密码以明文 JSON 写入 `~/.saicmotor/credentials.json`。虽设了 `0o600` 权限，但：
- 备份工具可能无意中捕获该文件
- 同机其他用户进程可读取（同 UID）
- 无离线攻击防护（磁盘取证、盗取笔记本）

**修复建议**：接入 OS 密钥链（Windows Credential Store / macOS Keychain / Linux `secret-tool`）；至少加密存储。

---

### 🟠 S3. `SAICMOTOR_SCRIPTS` 可导致任意代码执行（script.ts:43-47, 74）

**文件**：`packages/cli/src/engine/script.ts:43-47, 74`

**问题**：`findScript()` 接受 `SAICMOTOR_SCRIPTS` 环境变量拼接 catalog 中的 service/resource/method 名后 `await import(file)` 动态加载。若攻击者控制该环境变量或注入含 `../` 的 catalog 条目，即可执行任意 JS/TS 代码。

**修复建议**：
- 用 `path.resolve()` + `startsWith()` 做路径围栏
- 限制该环境变量仅开发模式生效（当前仅测试用，见 [[docs-are-process-artifacts-not-source-of-truth]]）

---

### 🟡 S4. Catalog 名缺路径遍历校验（schema/catalog.ts）

**文件**：`packages/cli/src/schema/catalog.ts:23-24`

**问题**：Zod schema 中 `Service.name`、resource 键名、`Method.id` 均接受任意字符串（含 `../`、`/`、`\`）。这些值流入 `findScript()` 做 `path.join()`，恶意插件 manifest 或 catalog JSON 可造成路径穿越。

**修复建议**：在 schema 加 `.refine(s => !s.includes('/') && !s.includes('\\') && !s.includes('..'))`。

---

### 🟢 S5. Token 片段暴露（cli/auth.ts:25）

**文件**：`packages/cli/src/cli/auth.ts:25`

**问题**：登录成功后打印 `token.slice(0, 8)`。虽然 8 字符不足以直接利用 token，但违反了"秘密不输出"原则。终端输出可被日志、录屏捕获。

**修复建议**：改用 hash 指纹：`crypto.createHash('sha256').update(token).digest('hex').slice(0, 8)`。

---

### 🟢 S6. state.json 缺文件权限（plugin/state.ts:31）

**文件**：`packages/cli/src/plugin/state.ts:31`

**问题**：`saveState()` 写 `state.json` 无显式 `mode`，依赖进程 umask。若 umask 宽松（如 `000`），state.json 可被同机其他用户读写。

**修复建议**：加 `{ mode: 0o600 }`，与 `store.ts` 保持一致。

---

### 🟢 S7. 模块级副作用：`saicmotor.config.json` 只在 import 时读一次（config.ts:32）

**文件**：`packages/cli/src/config.ts:32`

**问题**：`const pkgConfig = loadPackageConfig()` 在模块 import 时执行 `fs.readFileSync`，此后不再重读。若文件不存在或损坏，静默回退为空对象——无 warning。在实际使用中不太可能成为问题（文件随包发布），但这是脆弱的模块级副作用。

## 二、逻辑问题

### 🟠 L1. Catalog 解析失败硬阻断 CLI 启动（engine/catalog.ts:22）

**文件**：`packages/cli/src/engine/catalog.ts:22`

**问题**：核心 catalog 目录下任意一个 JSON 解析失败都会 `throw SaicmotorError("spec", ...)`，导致整个 CLI 无法启动（`index.ts:21` 在模块顶层调用 `loadCatalog()`）。

```typescript
// 现状：一个坏 JSON → CLI 全挂
catch { throw new SaicmotorError("spec", `无法加载 catalog: ${file}`); }
```

**修复建议**：catalog 加载失败应降级为 warning 并跳过该文件，不应阻断启动。参考插件 loader 的做法（`loader.ts:175` warning 而非 throw）。

---

### 🟠 L2. `code` 字段类型比较不一致——三处 `body.code` 检查方式不同

**涉及文件**：
- `packages/cli/src/auth/exchange.ts:54` — `Number(body.code) !== 0` ✅ 正确
- `packages/cli/src/auth/password.ts:31` — `body.code !== 0` ❌ 字符串 `"0"` 时误判
- `packages/cli/src/engine/run.ts:26` — `body.code !== 0` ❌ 同上

**问题**：只有 exchange.ts 对 `body.code` 做了 `Number()` 包装，另外两处直接比较。若服务端返回 `{ code: "0" }`，password 登录和 `checkEnvelope` 会误判为错误。

**修复建议**：统一为 `Number(body.code) !== 0`，或抽一个 `isErrorCode(body)` 工具函数。

---

### 🟠 L3. `handleError` 在处理 SaicmotorError 后缺少 return（cli/error.ts:4-11）

**文件**：`packages/cli/src/cli/error.ts:4-11`

```typescript
if (e instanceof SaicmotorError) {
  console.error(...);
  process.exit(e.exitCode);   // ← 此行后无 return
}
console.error(String(e));     // ← 正常 exit 不会到这，但测试 mock exit 时会穿透
process.exit(1);
```

**问题**：`process.exit` 通常终结进程，但在测试 mock 或极端时序下可能不立即退出，执行会穿透到 fallback `process.exit(1)`，导致双重错误输出和错误码覆盖。

**修复建议**：`process.exit(e.exitCode)` 后加 `return`（或 `void process.exit(...)` 然后用 `return` 显式控制流）。

---

### 🟡 L4. 插件冲突处理语义不一致（plugin/loader.ts:110-126）

**文件**：`packages/cli/src/plugin/loader.ts:110-126`

**问题**：当两个插件提供同名 service 时：
1. 第 114-117 行打印 warning：`"请用 plugin disable 处理"`
2. 第 122-126 行**静默丢弃**后来者的冲突 service

warning 暗示用户可以去操作，但实际上后来者的冲突 service 已被丢弃，即使用户 disable 了先加载的插件，后来者的 service 也不会重新出现（除非重新安装）。行为与提示不一致。

**修复建议**：要么明确告知"已自动丢弃"，要么不丢弃而是全部保留并在运行时检查（让 disable 生效后自动恢复）。

---

### 🟡 L5. npm 卸载失败被静默吞 + state 仍被删除（plugin-cmds.ts:130-132）

**文件**：`packages/cli/src/cli/plugin-cmds.ts:130-132`

**问题**：`uninstallPluginLogic()` 中 `npm uninstall` 失败被空 catch 吞掉，但后续仍删除 state 并报告成功：

```typescript
try { execSync(`npm uninstall ...`); }
catch { /* npm 卸载失败不阻断后续清理 */ }
delete state.plugins[full];  // state 已删除
```

结果：用户看到"已卸载"，state 中也没了，但 npm 包实际还在。`plugin list` 不再展示（因 state 被删），但下次 `plugin install` 同名包时 npm 可能因为已安装而行为异常。

**修复建议**：npm 卸载失败时应向用户发出 warning，不应静默继续。

---

### 🟡 L6. 插件脚本的 `UpstreamError` 不是 `SaicmotorError` 子类

**涉及文件**：
- `packages/plugin-leave/scripts/leave/applications/submit.ts`
- `packages/plugin-attendance/scripts/attendance/corrections/submit.ts`

**问题**：两个参考插件脚本定义了本地 `class UpstreamError extends Error`（非 `SaicmotorError`），脚本中 HTTP ≥ 400 抛此错误。错误传播到 `executeScript` → `runMethod` → Commander action → `handleError`。由于不是 `SaicmotorError` 实例，走不到分类错误输出，直接 `String(e)` + `exit(1)`——丢失结构化信封和正确退出码。

**修复建议**：SDK 应 export 一个 `SaicmotorError`（或其插件可用版本）供脚本使用；或让 `handleError` 对普通 Error 也做基本格式化。

---

### 🟡 L7. `findScript` 每次调用重新加载全部插件（engine/script.ts:53）

**文件**：`packages/cli/src/engine/script.ts:53`

**问题**：每执行一个业务命令，`findScript()` 都调用 `loadPlugins(loadConfig())`，重新读 config.json、state.json、扫描 linked/ 和 node_modules/、解析全部 manifest。插件在 CLI 启动时已在 `cli/index.ts:22` 加载过一次，但结果没有传递到 `findScript`。

**修复建议**：缓存插件列表，或由调用方（`runMethod`）传入已加载的插件。

---

### 🟢 L8. `skillsAlreadyInstalled()` 任意一个客户端存在即判为已安装（install/skills.ts:30-37）

**文件**：`packages/cli/src/install/skills.ts:30-37`

**问题**：检查"已安装"是通过扫描 AI 客户端 skills 目录下是否存在同名目录。但如果用户手动删了其中一个客户端下的 skill（如只删了 CodeBuddy 的），函数返回 `true`（因为 Claude 的还在），`saicmotor install` 会跳过注册，导致 CodeBuddy 永远缺这个 skill。

**修复建议**：改为检查**所有**客户端的**所有**核心 skills 是否都存在，缺少任何一个都应该触发补救。或用 `--force` 全量重装规避。

---

### 🟢 L9. Catalog glob 支持实际不完整（plugin/loader.ts:158-162）

**文件**：`packages/cli/src/plugin/loader.ts:158-162`

**问题**：`manifest.catalog` 声明支持 glob 列表，但 `loadPluginServices()` 的实际实现只支持 `catalog/services/*.json`，任何不含 `"services"` 的 glob 会被跳过（第 162 行 `continue`）。类型系统暗示了比实际实现更强的能力。

**修复建议**：要么实现真正的 glob 匹配（`minimatch`），要么在 manifest schema 中限制为固定路径而非 glob。

## 三、代码质量

### 🟡 C1. 类型定义重复（CLI ↔ SDK）

**涉及文件**：
- `packages/cli/src/engine/script.ts:11-20` ↔ `packages/sdk/src/context.ts:8-24`（ScriptContext, ScriptFn, RunResult）
- `packages/cli/src/schema/catalog.ts:3-34` ↔ `packages/sdk/src/catalog-types.ts:2-28`（Field, Method, Resource, Service）
- `packages/cli/src/config.ts:6-22` ↔ `packages/sdk/src/config-types.ts:2-18`（AuthConfig, Config）

**问题**：CLI 侧用 Zod schema（含运行时校验），SDK 侧用纯 TypeScript interface（仅供插件类型引用）。两套定义需人工保持同步，当前注释 `"与 packages/cli/src/config.ts 保持一致的接口子集"` 证明了维护负担。

**修复建议**：SDK 应从 CLI 的 zod schema 导出类型（`z.infer`），从根本上消除重复。SDK 已依赖 zod，技术可行。

---

### 🟡 C2. `any` 类型泄露（8 处）

**涉及文件**：
- `plugin-cmds.ts:65` — `catch (e: any)`
- `plugin-cmds.ts:209` — `catch (e: any)`
- `tooling-cmds.ts:175` — `catch (e: any)`
- `registrar.ts:47, 89` — `catch (e: any)`
- `loader.ts:92` — `catch (e: any)`
- `loader.ts:175` — `catch (_e: any)`

**问题**：8 处 `catch` 使用了 `any` 类型，应使用 `unknown` 并做类型收窄。TS 严格模式下 `any` 绕过类型检查。

---

### 🟡 C3. Plugin catalog 解析错误静默丢弃（plugin/loader.ts:175）

**文件**：`packages/cli/src/plugin/loader.ts:175`

**问题**：`loadPluginServices()` 中单个 catalog JSON 解析失败被 `catch (_e: any)` 静默吞掉，不用 warning 也不上报。用户安装了一个插件，其中某个 service 的 catalog 坏了，该 service 会无声消失。

**修复建议**：至少 push 一个 warning，让用户知道哪个插件的哪个 catalog 文件有问题。

---

### 🟡 C4. `CORE_VERSION` 硬编码未从 package.json 读取（plugin/loader.ts:60）

**文件**：`packages/cli/src/plugin/loader.ts:60`

**问题**：`const CORE_VERSION = "0.8.0"` 与 `cli/index.ts:16` 的 `program.version("0.8.0")` 是两处独立硬编码。版本升级时需手动同步，否则 `engine` 兼容检查会拒绝本应兼容的插件。

**修复建议**：从 `package.json` 读取或至少抽为单一常量（如 `config.ts` 导出）。

---

### 🟢 C5. 空 catch 块缺少注释（9 处）

关键位置：`plugin-cmds.ts:130` 的 npm 卸载失败 catch 无任何注释，审查时需猜测是否是刻意行为。

---

### 🟢 C6. 生成模板中 SDK 版本号用 `*`（tooling-cmds.ts:47）

**文件**：`packages/cli/src/cli/tooling-cmds.ts:47`

**问题**：`createPluginLogic()` 生成的 `package.json` 中 `"@saicmotor/sdk": "*"` 使用通配版本，不具备可重现性。

**修复建议**：用具体版本范围，如 `"^0.8.0"`。

---

### 🟢 C7. `validateManifest` 与 `definePlugin` 功能重复（sdk/src/manifest.ts:24-31）

**文件**：`packages/sdk/src/manifest.ts:24-31`

**问题**：两个函数实现完全相同（都是 `PluginManifestSchema.parse()`），都被 export，但生产代码中无人调用（CLI 直接调 `PluginManifestSchema.parse`）。仅测试使用。

**修复建议**：合并为 `validateManifest`，或标记 `definePlugin` 为 `@deprecated`。

## 四、架构 & 耦合

### 🟡 A1. `loadPlugins(_config)` 参数未使用（plugin/loader.ts:66）

**文件**：`packages/cli/src/plugin/loader.ts:66`

**问题**：`loadPlugins(_config: Config)` 接收 config 参数但从不使用。4 处调用方都传了 config，但实际上 `loadPlugins` 完全自治——它自己读 state、自己扫描文件系统。暗示了未实现的功能或过度设计。

**修复建议**：要么实现 config 驱动的过滤/行为差异化，要么移除参数。

---

### 🟢 A2. `scriptFileFor()` 是死代码（engine/script.ts:22-24）

**文件**：`packages/cli/src/engine/script.ts:22-24`

**问题**：`scriptFileFor()` 被 export，但生产代码中无调用者。唯一引用在 `test/unit/script.test.ts` 中。实际脚本解析走 `findScript()`，不走此函数。

**修复建议**：删除或标记为 `@internal`。

---

### 🟢 A3. `validateManifest` / `definePlugin` 功能完全重复（sdk/src/manifest.ts:24-31）

**文件**：`packages/sdk/src/manifest.ts:24-31`

**问题**：两个函数实现相同（`PluginManifestSchema.parse()`），均被 export，但生产代码中直接调用 `PluginManifestSchema.parse()`——这两个 wrapper 无人用。

**修复建议**：合并为一个，或标记 deprecated。

---

### 🟢 A4. `scriptsDir()` 是死代码（config.ts:78-80）

**文件**：`packages/cli/src/config.ts:78-80`

**问题**：`scriptsDir()` 函数在全部 production 代码中无调用者。`SAICMOTOR_SCRIPTS` 环境变量仅在 `findScript()` 中直接读取，不经过此函数。

**修复建议**：删除。

---

### 🟢 A5. 三个插件包 `src/index.ts` 只有占位注释

**文件**：`packages/plugin-{leave,attendance,user}/src/index.ts`

**问题**：各文件只有一行注释（如 `// @saicmotor/plugin-leave — placeholder`），export 为空。这是脚手架残留，目前无功能。

**修复建议**：保留或删除均可（作为模板骨架有参考价值），但应加 TODO 注释说明预期用途。

---

### 🟢 A6. junction symlink 在非 Windows 平台总是降级为 copy（registrar.ts:40）

**文件**：`packages/cli/src/plugin/registrar.ts:40`

**问题**：`registerSkill()` 使用 Windows-only 的 `"junction"` 类型创建符号链接，非 Windows 上必失败降级为 `copyDirSync`。降级后的目录是静态快照——源码 skill 更新不会自动反映到 AI 客户端。用户需要 `saicmotor install --force` 重新复制。

**修复建议**：macOS/Linux 上用 `"dir"` 类型 symlink（无需管理员），仅 Windows 用 junction。

---

### 🟢 A7. SDK `context.ts` 泄露 CLI 实现细节（sdk/src/context.ts:14）

**文件**：`packages/sdk/src/context.ts:14`

**问题**：`ScriptContext.ensureToken: () => Promise<string>` 直接暴露 CLI 的 token 缓存/刷新机制。插件开发者看到此类型不清楚"token 从哪来""何时刷新"。

**修复建议**：文档补充或抽象为 `auth: { getToken(): Promise<string> }`。

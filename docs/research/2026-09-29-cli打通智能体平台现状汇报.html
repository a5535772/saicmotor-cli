AI 智能体接入 · 现状说明

智能体怎么够到公司内部系统

面向公司领导 · 非技术视角 现状与边界 通俗比喻 约 15 分钟
01先讲结论
用一句话说清当前局面，后面所有内容都是这句话的展开。
🟢
跑在员工自己电脑上的智能体，现在就能用 像 Claude Code、Trae、CodeBuddy 这类"终端智能体"，装上我们自研的一个命令行工具，就能帮员工查请假、查考勤。这条路已经走通，具备条件。 → 相当于在员工自己的房间里安排了一名办事员，随时使唤
🔴
飞书、腾讯 ADP 这类云端平台上的智能体，目前进不去 平台只提供"插件、技能、工作流"这类网络服务式通道，不给第三方工具开安装入口，所以我们的工具装不进它的云端环境。 → 相当于酒店房间只准用酒店自带的设施，自己的家具搬不进去
🟡
症结不在我们，而在平台一侧 第三方工具要进入云端，平台必须同时打开"三扇门"：安装通道、持久化、凭证注入。这三把钥匙都握在平台手里，我们单方面解决不了。 → 是行业现状决定的边界，不是我们的产品没做好
一句话总纲：办事员（工具）必须和员工（智能体）待在同一个房间里，才能帮上忙；而房间是物业（平台）给的、钥匙也是物业管的。

难点就在中间这一段，要解决三件事 ① 通道：用什么方式去调用系统接口；② 身份：系统怎么知道"这次是替哪个员工办的"；③ 安全：怎么保证调用范围可控、可审计、能追溯。 再强的模型，如果平台不给它开门、不给装工具的地方、不告诉它当前用户是谁，也只能"原地聪明"
企业用 AI 的瓶颈，正从"模型够不够聪明"转向"通道、身份、安全这最后一公里"。
03核心原理：工具必须和智能体"住在一起"
这是理解全部现象的一把钥匙，用生活化比喻讲清楚。
比喻对应概念
企业里的业务系统（请假、考勤、人事）办公楼里一个个部门办事窗口
AI 智能体一名聪明但没有工牌的新员工
CLI（命令行工具）一名驻场办事员：你告诉他办什么，他跑去窗口替你办
运行智能体的环境这名员工办公和住宿的房间
密码、令牌等凭证开门用的钥匙和门禁卡
飞书、腾讯、字节等平台方整栋大楼的物业
关键机制：智能体调用工具，不是打电话、不是发微信，而是在同一个房间里直接"喊人出来办事"。这意味着——工具必须装在智能体所在的同一个环境里（同一台电脑、同一个容器）。装到别处，就喊不到。这不是我们的设计选择，而是系统的工作方式决定的。
三种方式在两端的效果：MCP / Skills 都能用，CLI 只有本地能用

为什么结果不一样？关键在"要不要搬进房间"：
· CLI 是"驻场办事员"，必须和智能体住在同一个房间——本地有自己的长住房，住得下 ✅；云端是临时酒店房间，不给装、存不住、没钥匙 ❌。
· MCP 是"连出去的总台"、Skills 是"翻开的操作手册"——都不需要搬进房间，所以本地、云端都能用 ✅。
🖥️ 本地长住房 · 终端智能体
房间长期存在，想装什么就装什么
代表：Claude Code、Trae、CodeBuddy、Cursor 等。跑在员工自己电脑上，装上的工具一直在，重启也在，员工有完全支配权。
☁️ 云端酒店房间 · 平台托管
临时房间，任务结束就销毁
代表：腾讯 ADP、字节 Coze、飞书 Aily 等。每接一个任务临时开一个"房间"，用完就收回，下次可能是个全新的空房间。
终端智能体有自己的长住房，工具天然适配；云端平台是临时酒店房间，这就是后面所有"装不进去"的根源。
04三种连接方式
智能体和内部系统之间隔条河，业界目前有三座桥，各有用途，常常组合使用。
🧑‍💼
CLI（驻场办事员）
把工具装进智能体的房间，直接干活。任何能"开进程"的智能体都能用，调试直观；代价是每次调用要起进程、安全边界较粗。
🏢
MCP（标准总台）
行业标准协议，智能体用统一方式调用外部工具；凭证留在系统一侧、不进智能体环境，便于鉴权审计。代价是每接一个系统要建一个"总台"。
📖
Skills（操作手册）
教智能体"什么情况、按什么套路、分几步办"。和 MCP 互补——手册 + 窗口，两者常捆绑提供，而非二选一。
维度CLIMCPSkills
通俗理解 驻场办事员 标准化总台 操作手册
本质 可执行程序 调用协议 说明书 + 脚本
凭证（钥匙）在哪 智能体环境内 系统一侧（不进智能体） 视手册调用的工具而定
安全细粒度 较粗 强 取决于底层
💡 一个值得注意的趋势：Claude Code、OpenAI、Google，以及国内的飞书、钉钉、企业微信，都在推"为人和 AI 同时设计"的官方命令行工具，说明 CLI 这条路的方向是被行业验证的。但"趋势"不等于"平台已经开放"——云端平台如何接纳第三方工具，仍是下面要讲的行业空白。
MCP 管连接、Skills 教方法、CLI 直接干活。前两者是当今主流，"AI 原生 CLI"是明确趋势；聪明的做法通常是三者组合，而不是迷信任何一个。
05平台现状：一边畅通，一边关门
分两类平台看，结果截然不同。
🟢 终端类 · 畅通（现在能用）
装上我们的工具，跟装普通软件一样简单
Claude Code、Trae、CodeBuddy、Gemini CLI、Cursor、Windsurf。共性：跑在员工本地，一条命令即可安装，随后智能体就能调用。
🔴 云端托管 · 关门（进不去）
只有"网络服务式"通道，没有工具安装入口
腾讯 ADP、字节 Coze、飞书 Aily、阿里百炼、文心、OpenAI。共性：只提供插件、技能、MCP、工作流，第三方工具装不进云端容器。
❓ 常被问到：飞书容器里明明有飞书自己的 CLI，为什么说第三方进不去？
那是飞书自家的工具，走的是"官方预装"待遇：凭证由平台托管（钥匙在物业手里），用户不用自己粘贴任何密钥。这证明不了第三方工具也能进。

打个比方：酒店房间里放着一把印有酒店 logo 的雨伞，那是酒店自己放的、统一管理的；这不意味着你可以把自己的家具搬进房间、并且指望换了房间之后家具还在。
截至 2026 年 9 月，没有任何一家主流云端平台把"用户自带的第三方工具装进云端容器并持久化"作为产品能力提供。平台的官方通道高度统一：插件 / 技能、MCP、工作流、连接器——本质都是把外部能力当"网络服务"在运行时调用，而不是把外部程序装进去。
06瓶颈定性：三扇门的钥匙在平台手里
第三方工具要进入云端正常工作，以下三个条件缺一不可，而它们都由平台决定。
门 ①
安装通道
允许第三方程序进入执行环境（自定义镜像、官方安装入口或扩展机制）。
由谁决定：平台
门 ②
持久化
容器销毁后，工具和绑定关系还能保留，不必每次重装。
由谁决定：平台
门 ③
凭证注入
工具能以"当前对话员工"的身份合法调用系统，凭证有安全的注入与托管机制。
由谁决定：平台（+ 企业 IT 配合）
专门讲一下"身份"：两层身份，绝不能混
身份层回答的问题智能体看得到吗
应用 / 机器人身份 这个智能体"作为哪个应用"在运行 看不到凭证本身
终端用户身份 这次对话"是哪个员工在操作" 看得到姓名、工号，但没有对应的密码 / 令牌
⚠️ 两个常见误区：
· "知道用户是谁，就能替他调系统" —— 不是。知道是谁只是一个"身份标识"，真正调用系统还要有凭证（钥匙）。
· "用户身份权限一定比机器人大" —— 不一定。实际权限 =「应用申请到的」∩「用户本人拥有的」，是交集关系。
装得进、留得住、拿得到钥匙——三扇门都由平台控制。我们能做的是把问题提清楚、把试点做扎实，而不是替平台去开门。
07现有的基础（客观说明）
过去一段时间的工作，已经搭起了一个可用的起点，但离"云端可用"还有明显距离。
1
一个自研的命令行工具：核心引擎已具备，并做了三个业务插件作为参考实现——请假、考勤、用户信息。
2
身份打通已完成验证：员工用飞书身份登录，换取各业务系统的访问令牌（单点登录方向），方向与上面的"两层身份"模型一致。
3
工程化能力：通过公司内部 npm 仓库分发，插件可独立安装、独立升级，版本不兼容会被明确拦下。
📌 需要客观说明的是：这些是"工具本身能做什么"的准备工作；云端平台上"装不进去"是行业现状决定的边界，不会因为有这些准备就改变。两者是不同的两件事。
08下一步：两条工作线
不纠结"谁取代谁"，把工作切成两条目标不同、互不拖累的并行线。
维度线路一：云端平台 · 原生方式线路二：CLI · 终端试点
目标 让"查请假、查考勤"在云端平台上先跑通 验证并坐实自研工具的价值
平台 飞书、腾讯 ADP 等 CodeBuddy、Trae 等终端智能体
方式 MCP / Skill / 插件（平台原生） 自研命令行工具
当前状态 待可行性验证 已有基础，可试点
边界 受平台规则约束 云端平台暂不支持，边界已明确
时间线（示意）
已完成
核心引擎 + 三个业务插件 + 飞书登录验证 + 内部分发
近期
终端智能体小范围试点；云端平台 MCP/Skill 可行性验证；整理需平台回答的问题
中期
试点扩面、身份与审计完善；跟踪平台开放进展
长期
随行业"云端 + 本机执行"合流，实现一套业务能力、多环境通用
💡 一个定位说明：云端线路上建设的 MCP / Skill 成果，是"为在该平台办事而穿的平台制服"，与自研 CLI 是同一业务能力在不同环境下的不同形态，不是重复竞争。
09需要平台方回答的问题（供参考）
这些是行业层面的开放问题，记录备查；是否推动、何时推动，视公司后续需要而定。
1
平台是否允许第三方程序装进执行环境？通过什么机制（自定义镜像、官方扩展入口）？
2
执行环境中哪些目录能跨会话持久化？工具和配置能否长期保留？
3
平台能否安全传递终端用户身份？以什么格式、是否带签名、能否防伪造？
4
是否托管用户对第三方应用的授权（如 OAuth）？凭证生命周期如何管理？
5
对外部系统调用的审计日志、限流、权限裁剪，平台提供哪些能力？
6
平台在"云端环境调用用户本机资源"方向上的路线图是怎样的？
📌 这份清单也是判断"平台的门何时开、开了多大"的一把标尺。一旦某个平台真正开放扩展能力，我们的工具就能第一时间接入。
10一页总结
如果只记住一页，请记住这一页。
1️⃣
现状：三条桥，两种房间 智能体连企业系统有三种方式——CLI（驻场办事）、MCP（标准总台）、Skills（操作手册）。智能体有两种运行环境：本地长住房（终端智能体）与云端酒店房间（平台托管）。
2️⃣
边界：CLI 必须与智能体同住；云端的门，钥匙在平台手里 终端智能体上，CLI 现在就能装、就能用；云端平台上要工作，平台必须同时给出安装通道、持久化、凭证注入三个条件——截至今天，还没有主流平台开放这些能力。
3️⃣
下一步：两条线并行 云端平台上按它的规矩用原生方式先把业务跑通；终端场景下把自研工具做实试点。工具已经在手，差的是平台开门的时机。

术语通俗解释
API（接口）业务系统对外提供的"办事窗口"，程序通过它查询或提交数据
CLI（命令行工具）用文字命令操作的程序；智能体在"同房间"里调用它
容器 / 沙箱程序运行的隔离"房间"；云端通常临时分配、用完销毁
MCP智能体发现与调用外部工具的行业标准协议
MCP Server系统一侧按标准提供的服务；凭证保存在此，不进智能体环境
Skills（技能）教智能体怎么办事的"操作手册"及配套脚本，按需加载
SSO / OAuth / OIDC单点登录与常见安全授权 / 身份协议：登录一次，多系统认你，平台代持凭证
Token（令牌）系统发给已认证用户的"临时门票"，有有效期、可独立刷新
应用身份 vs 用户身份"作为哪个应用运行" vs "哪个员工在操作"，两层不可混

## 开篇 · 导言：这堂课要回答三个问题

各位同事，大家好。

过去一段时间，我们围绕一个问题做了不少工作：**怎么让 AI 智能体替员工调用企业内部的系统**——比如查请假余额、提交考勤、查询员工信息。我们自研的工具 `saicmotor-cli` 已经有了雏形，但在推广过程中遇到一个现象：**同一个工具，在 Trae、CodeBuddy 这类智能体上可以用，在飞书智能体、腾讯 ADP 这类平台上却装不进去。**

今天这堂课，不堆术语，主要回答三个问题：

1. **AI 智能体到底是怎么"够到"企业内部系统的？**（第一至第三讲）
2. **为什么我们的 CLI 工具在有的平台能用、有的平台不能用？问题出在哪一侧？**（第四至第五讲）
3. **我们已经有什么、现在应该做什么？**（第六至第七讲）

课程中我会用一个生活化的比喻贯穿始终，先在这里立好，后面反复使用：

| 比喻 | 对应概念 |
|------|----------|
| 企业里的各个业务系统（请假、考勤、人事） | 办公楼里一个个**部门办事窗口** |
| AI 智能体 | 一名**聪明但没有工牌的新员工** |
| CLI（命令行工具） | 一名**驻场办事员**：你告诉他办什么，他跑去窗口替你办 |
| 运行智能体的环境 | 这名员工**办公和住宿的房间** |
| 密码、令牌（Token）等凭证 | 开门用的**钥匙和门禁卡** |
| 飞书、腾讯、字节等平台方 | 整栋大楼的**物业** |

先记住一句话，它是今天全部内容的总纲：

> **办事员（CLI）必须和员工（智能体）待在同一个房间里，才能帮上忙。而房间是物业给的，钥匙也是物业管的。**

下面开课。

## 第一讲 · 问题：聪明的员工，缺的是"门禁"和"跑腿能力"

**本讲要点**

- AI 的"聪明"（理解语言、做判断）和"办事"（操作系统）是两种能力。
- 企业真正的难点不在让 AI 听懂话，而在让它**安全地够到内部系统**。

### 1.1 智能体替员工办事，前提是"够得着"

今天的大模型，理解"帮我查一下我还剩多少年假"这句话已经毫无困难。但听懂之后，它需要真的跑到**考勤休假系统**里把数字取出来。这一步，行业里通常称为"最后一公里"：

```
员工说话 → 智能体理解意图 → ？？？ → 企业内部系统返回结果
                              ↑
                        难点就在这一段
```

中间这一段要解决三件事：

1. **通道**：用什么方式去调用系统的接口（API）？
2. **身份**：系统怎么知道"这次请求是替哪个员工办的"？能不能看到这个员工该看到的数据？
3. **安全**：怎么保证调用范围可控、行为可审计、出了问题能追溯？

### 1.2 这不是"AI 聪不聪明"的问题

需要特别说明：这一段的难度与模型能力基本无关。再强的模型，如果平台不给它开门、不给它装工具的地方、不告诉它当前用户是谁，它也只能"原地聪明"。

这就是我们这门课聚焦"连接方式"而不是"模型选型"的原因。

> **一句话小结**：企业用 AI 的瓶颈，正从"模型够不够聪明"转向"通道、身份、安全这最后一公里"。

## 第二讲 · 核心原理：CLI 必须和智能体"住在一起"

**本讲要点**

- CLI 是智能体通过"开子进程"方式调用的驻场办事员。
- 子进程只能开在同一个房间里——所以 CLI 装在哪里，取决于智能体运行在哪里。
- 智能体有两种"宿舍"：本地长住房和云端酒店式房间。

### 2.1 什么是 CLI

CLI（Command Line Interface，命令行接口）是一种通过输入文字命令来操作软件的程序。软件工程师几十年来一直用这种方式工作：敲一行命令，程序执行，返回结果。例如我们的工具：

```bash
saicmotor leave balance query      # 查询年假余额
saicmotor attendance record list   # 查询考勤记录
```

过去 CLI 是给**人**用的。2025 年以来出现了一个重要变化：**CLI 同时开始为 AI 智能体而设计**——命令的输出默认采用机器容易解析的 JSON 格式，附带"操作说明书"（Skills），智能体读了说明书就知道什么时候该敲哪条命令。飞书官方的 lark-cli、我们的 saicmotor-cli，都是这种"人机两用"的新形态。

### 2.2 智能体怎么调用 CLI：在同一个房间里"开子进程"

这是今天最关键的技术原理，请允许我讲细一点。

智能体调用 CLI，**不是打电话、不是发微信，而是在自己的房间里直接喊一个人出来办事**。操作系统里这个动作叫**开启子进程**：

- 智能体是父进程；它在本机的 PATH（可以理解为"房间里的值班表"）上找到 CLI 这个可执行程序；
- 然后 fork/exec（可以理解为"喊它出场"），把命令交给它，等它办完，从标准输出里读结果。

各大主流智能体的官方文档对这一机制都有明确表述：

- Claude Code（Anthropic）官方文档："Bash 工具让每条命令运行在一个**独立的进程**中"，沙箱边界覆盖"每条命令**及其子进程**"。
- Gemini CLI（Google）内置 `run_shell_command` 工具，底层就是操作系统的子进程机制，让模型"直接在你的系统 Shell 上执行命令"。
- Cursor 官方文档："直接在你的终端中运行 Shell 命令"，其沙箱约束的是"整棵子进程树"。
- TraeCode CLI（字节）、CodeBuddy（腾讯）也都以 Bash/终端工具作为智能体执行命令的标准方式。

由此可以得到一个严格的推论：

> **CLI 必须安装在与智能体相同的执行环境里——同一台电脑、同一个容器、同一个沙箱。如果 CLI 在另一个环境里，智能体"喊"不到它，这种用法就不成立。**

这不是我们的设计选择，而是操作系统的工作方式决定的。

### 2.3 两种"宿舍"：本地长住房 vs 云端酒店房间

智能体运行在哪里？行业里实际上有两类完全不同的"宿舍"，理解了它们的区别，后面所有现象都一目了然。

**第一种：本地长住房——终端类智能体**

代表：Claude Code、Trae/TraeCode CLI、CodeBuddy Code、Gemini CLI、Cursor、Windsurf。

- 它们运行在**员工自己的电脑上**（或员工自己掌控的服务器上）；
- 房间长期存在，装上的东西一直在，重启也在；
- 员工对房间有完全的支配权：想装什么工具就装什么。

**第二种：云端酒店式房间——平台托管型智能体**

代表：腾讯 ADP、字节 Coze、飞书 Aily（以及阿里百炼、文心智能体等）。

- 它们运行在**平台云端的数据中心**，员工通过网页或飞书对话窗口与它交流；
- 每接到一个任务，平台临时分配一个房间（沙箱容器），**任务结束房间就收回、销毁**；
- 下次对话，领到的可能是一个全新的空房间。只有少数指定目录（通常是"工作产物"和"工具绑定"两类目录）被允许保留下来。

以飞书 Aily 为例，根据已有调研材料，其执行模型为：每次任务启动一个独立的沙箱容器（约 1 核 CPU / 4 GB 内存），任务结束容器即释放；仅 `~/.aily/workspace/`（工作产物、记忆）与 `~/.aily/.cli/`（工具绑定）跨会话保留。其他云端平台的具体目录清单大多不公开，但"容器临时、白名单目录持久化"是共同思路。

### 2.4 一张图看懂

```
【终端类智能体】员工的电脑（长住房）
 ┌──────────────────────────────────────┐
 │  智能体（长住）                        │
 │      │ 喊子进程                        │
 │      ▼                                │
 │  CLI 办事员（已安装，长期在岗）  ✅     │
 └──────────────────────────────────────┘

【平台托管型智能体】云端数据中心（酒店房间）
 ┌──────────────────────────────────────┐
 │  本次任务的临时房间（退房即销毁）        │
 │      │ 喊子进程                        │
 │      ▼                                │
 │  ？？？ 自己带的办事员没登记、住不进来 ❌ │
 └──────────────────────────────────────┘
```

> **一句话小结**：CLI 是靠"同住一个房间、子进程传唤"工作的。终端智能体有自己的长住房，CLI 天然适配；云端平台是临时酒店房间，这就为后面所有的"装不进去"埋下了根源。

## 第三讲 · 三种搭桥方式：CLI、MCP、Skills

**本讲要点**

- 目前业界把智能体与外部系统连起来，主要有三种方式。
- MCP 和 Skills 是当今主流；"官方 CLI 为 AI 设计"是正在兴起的新趋势。
- 三者各有适用场景，不是互相替代，而是常常组合使用。

智能体和企业系统之间隔着一条河。怎么过河？业界目前有三座桥。

### 3.1 第一座桥：CLI（子进程调用）

即第二讲讲的方式：把 CLI 装进智能体的房间，智能体通过子进程使唤它。

**优点**

- **智能体侧零适配**：任何能开子进程的智能体都能用，不需要平台为它做任何特殊改造；
- **能力完整、调试直观**：命令行能做的事它都能做，工程师在终端里可以直接复现问题；
- **知识沉淀丰富**：CLI 已经存在几十年，模型对"怎么用命令行"有大量训练积累。

**缺点**

- **每次调用要起一个进程**，高频大批量调用时开销不小；
- **输出要靠程序解析**，所以新一代 CLI 都默认提供 JSON 输出；
- **安全边界较粗**：CLI 拿到谁的凭证，通常就能以那个人的身份做这个工具范围内的一切事，细粒度管控需要额外机制（第五讲会展开）。

### 3.2 第二座桥：MCP（标准化的"总台服务"）

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年 11 月开源的一套标准协议，解决的问题是：**智能体用统一的方式发现和调用外部工具，而不必为每个系统单独对接。**

打个比方：CLI 是"驻场办事员"，MCP 则像在每个系统门口设一个**标准化总台**，无论哪个系统，窗口规格、问话方式完全一样，智能体学会一次，处处通用。

它的架构是：业务系统一侧运行一个 MCP Server（独立部署的服务），智能体作为 MCP Client 通过协议调用它。**业务系统的凭证只保存在 Server 侧，永远不进入智能体所在的环境。**

**发展速度可以用"席卷行业"形容**（均有公开来源）：

- 2024-11：Anthropic 发布 MCP；
- 2025-03：OpenAI 宣布全线产品支持；
- 2025-04：Google 宣布 Gemini 支持，称其"正快速成为智能体时代的开放标准"；
- 2025-05：微软与 GitHub 在 Build 大会宣布加入，Azure、Windows 提供一方支持；
- 2025-12：MCP 被捐赠给新成立的 **Linux 基金会 Agentic AI 基金会（AAIF）** 中立治理，官方口径已有**超过 1 万个公开 MCP Server**；
- 2026-07：MCP 2 版规范将远程服务改为完全无状态，Server 可以直接跑在无状态的云函数上，大幅降低了运维门槛。

**优点**：行业共识标准、跨平台可移植；凭证集中在 Server 侧，便于统一鉴权、审计、限流；工具可以被智能体自动发现。

**缺点**：每接入一个系统，仍然需要建设（或部署）一个对应的 MCP Server；"终端用户身份如何跨 Server 安全透传"目前没有协议级的统一标准，需要组合方案（见第五讲）。

### 3.3 第三座桥：Skills（给智能体的"操作手册"）

Skills（技能）是把"做某类任务的操作说明和配套脚本"打包成一个文件夹，核心是一份 `SKILL.md` 说明书。智能体在任务相关时才翻开它，按手册操作。

- 2025-10：Anthropic 正式推出 Agent Skills；
- 2025-12：升级为**跨平台可移植的开放标准**（agentskills.io）；
- 增长数据：据 Vercel 2026 年 9 月发布的行业报告，其技能登记站在 **7 个月内收录了 100 万个技能、累计安装近 2.8 亿次**。

**Skills 与 MCP 的关系，是"手册"与"窗口"的关系，二者互补**：MCP 定义"怎么连接、怎么调用"；Skills 教智能体"什么情况下、按什么套路、分几步去办"。智能体完全可以"照着 Skill 手册，去调 MCP 窗口"。飞书 lark-cli 自带 26 个 Skills，Stripe 的官方方案则把 MCP Server 和 Skills 打包提供——业界的主流实践是两者捆绑，而非二选一。

### 3.4 三座桥对比

| 维度 | CLI | MCP | Skills |
|------|-----|-----|--------|
| 本质 | 可执行程序（驻场办事员） | 工具调用协议（标准化总台） | 说明书+脚本（SOP 手册） |
| 工作方式 | 智能体开启子进程 | 网络协议调用外部 Server | 智能体按需加载指令 |
| 平台需开放什么 | 允许安装、允许起进程、给凭证 | 允许配置 MCP 连接 | 允许加载技能 |
| 凭证位置 | 智能体所在环境内 | Server 侧（不进智能体侧） | 视手册里调用的工具而定 |
| 跨平台通用性 | 高（凡能起进程处皆可用） | 高（行业标准） | 中→高（开放标准推进中） |
| 细粒度安全控制 | 弱（边界粗，需补强） | 强（Server 统一鉴权） | 取决于底层调用方式 |
| 成熟度 | 老形态、新趋势 | 事实标准 | 快速普及中 |

### 3.5 一个重要的新趋势：官方 CLI 为 AI 而生

虽然 MCP、Skills 是当今主流桥接方式，但 2025 年以来出现了一个明确的新动向：**各大厂商纷纷推出"为人类和 AI 智能体同时设计"的官方 CLI**：

- 2025 年上半年：Claude Code、OpenAI Codex CLI、Google Gemini CLI 相继发布，终端成为大厂智能体的新战场；
- Stripe（国际支付平台）：把"安装官方 CLI"作为智能体接入的第一步；
- Cloudflare：**2026 年 9 月 28 日（就在本文写作前一天）**发布新 CLI，由接口定义自动生成 **3000 多个操作**，默认 JSON 输出、支持自然语言搜命令；
- 国内协作平台集体跟进：飞书 `lark-cli`（GitHub 约 1.7 万星，200+ 命令、26 个 Skills）、钉钉 `dingtalk-workspace-cli`、企业微信 `wecom-cli`。

TechCrunch 在 2025 年 7 月的报道中概括了这一转向："AI 编程工具正在转移到一个出人意料的地方——终端。"

这说明什么？**CLI 这条路的方向是被行业验证的。** 但请注意趋势与"平台已支持"是两回事——这些第一方 CLI 目前主要运行场景仍是终端/本地智能体，云端平台如何接纳第三方 CLI，下两讲就是答案。

> **一句话小结**：MCP 管连接、Skills 教方法、CLI 直接干活；前两者是当今主流，"AI 原生 CLI"是明确趋势。聪明的企业实践通常是三者组合，而非迷信任何一个。

## 第四讲 · 平台现状盘点：一边畅通，一边关门

**本讲要点**

- 终端类智能体：可安装任意 CLI，当前即可使用。
- 云端托管平台：第三方 CLI 没有官方入口，进不了容器。
- 飞书容器里确实有 lark-cli——但那是"自家物业预装、代管钥匙"的特例，不代表第三方 CLI 也能进。
- 截至今天，**没有任何主流平台原生支持第三方 CLI，也没有成熟的"远程 CLI 扩展市场"。**

### 4.1 终端派：CLI 的天然主场（✅ 可用）

| 平台 | 形态 | 调用本机 CLI 的机制 | 第三方 CLI |
|------|------|---------------------|------------|
| Claude Code | 本地终端 | Bash 工具，每条命令独立子进程；细粒度权限 + 可选沙箱 | 可安装 |
| Trae / TraeCode CLI（字节） | 本地终端/IDE | Bash 等工具，支持按命令授权 | 可安装 |
| CodeBuddy Code（腾讯） | 本地终端，npm 安装（`@tencent-ai/codebuddy-code`） | 终端工具 + MCP + Hooks | 可安装 |
| Gemini CLI（Google） | 本地终端，开源 | `run_shell_command` 子进程 + 策略引擎 | 可安装 |
| Cursor | 本地 IDE | 终端工具直接执行，沙箱约束子进程树 | 可安装 |
| Windsurf | 本地 IDE | 经许可运行终端命令，支持自动执行级别管控 | 可安装 |

**在这些平台上，安装我们的 saicmotor-cli 与安装 git 没有任何区别**：`npm install -g` 或 `npx` 即可，智能体随后就能通过子进程调用。

### 4.2 云端派：门没有为第三方 CLI 打开（❌ 不可用）

| 平台 | 云端执行形态 | 官方扩展通道 | 第三方 CLI 能否进容器 |
|------|--------------|--------------|----------------------|
| 腾讯 ADP（智能体开发平台） | "Claw 模式"云端工作空间；Agent Harness 统一调度、断点续跑、密钥托管 | Skills、连接器、工作流、OpenAPI | 未发现安装入口 |
| 字节 Coze（扣子） | 插件云端调用；"Claw 会话"云端托管实例 | 插件、工作流、MCP、知识库 | 未发现安装入口 |
| 飞书 Aily | "云端电脑/沙箱"：含浏览器、终端、文件系统、网络；任务级容器 | 技能（含技能市场）、MCP、工作流、连接器 | 第三方无官方通道 |
| 阿里百炼 / 文心等 | 云端受控沙箱 | 插件、MCP、工作流、代码节点 | 未发现安装入口 |
| OpenAI（GPTs / 云端 Codex） | 临时云端环境（浏览器、终端、虚拟电脑） | Actions、MCP、连接器 | 未发现安装入口 |

需要特别说明两点，避免误读：

**其一，腾讯 ADP 是否原生支持 MCP？** 在本次可获取的公开产品页与文档中未检索到以"MCP"命名的明确条目（其完整功能文档为动态渲染、无法完整读取），因此严谨的表述是"**公开资料未确认**"，其公开主打的扩展方式是 Skills、连接器和工作流。这不影响本讲结论：无论 MCP 支持与否，第三方 CLI 都没有安装入口。

**其二，字节确实有一个 `@coze/cli`（扣子命令行工具），但它是装在开发者自己电脑上的"本地管理客户端"**——用来在终端管理项目、部署、查看云端 Claw 会话。它不是"跑在扣子云容器里的第三方 CLI"，方向恰好相反，不能作为"云端平台支持 CLI"的证据。

### 4.3 重点案例：飞书容器里的 lark-cli，是怎么回事

很多同事会问：飞书智能体的容器里明明就有飞书 CLI，凭什么说 CLI 进不去？

这是一个非常关键的"特例与通例"之辨。事实是：

1. **lark-cli 是飞书的第一方（自家）CLI**，由飞书官方团队维护。它进入 Aily 环境，走的是**官方注入/预装待遇**：以 npm 包加 Skills 的方式安装进执行环境，凭证由平台侧绑定，用户无需自己粘贴任何密钥。
2. **凭证不进容器**：飞书凭证由平台的凭证中心托管。我们在 lark-cli 开源代码中可以清楚看到这种"侧车（Sidecar）"模式的完整设计——容器内的 CLI 只持有一个"哨兵"标识，真正的请求经 HMAC 签名后发给容器外、运行在可信环境中的代理服务，由代理用真实凭证调用飞书接口，再把结果返回。简单说：**办事员人在房间里，但钥匙在房间外的物业手里，每次开门由物业代开。**
3. **第三方 CLI 不享有同等待遇**：没有平台官方的安装通道，也没有平台为它代管凭证。哪怕利用终端和持久化目录"临时下载一个、凑合着用"，也会面临"容器一销毁就要重装、用户凭证无处安放"的问题——这是手工变通，不是受治理的产品能力。

打个比方：酒店房间里确实放着一把印有酒店 logo 的雨伞（第一方 CLI），那是酒店自己放的、统一管理的；但这不意味着你可以把自己的家具搬进房间、并且指望换了房间之后家具还在。

### 4.4 本讲的明确结论

> **截至 2026 年 9 月，没有任何一家主流托管智能体平台，把"用户自带的第三方 CLI 安装进云端容器并持久化"作为原生、受治理的产品能力提供；也没有成熟的"远程 CLI 扩展市场"。**
>
> 平台的官方扩展通道高度统一：**插件/技能、MCP、工作流节点、连接器**——本质都是把外部能力当作"网络服务"在运行时调用，而不是把外部的可执行程序装进容器。

唯一的两个例外情形也很清楚，且都不等于"平台开放"：

- **自托管开源平台**（如私有化部署 Dify）：房子是你自己的，你可以随意改造镜像、预装任何 CLI——自由来自"自己当物业"；
- **本机执行通道**：飞书等平台正在做"云端主体 + 经用户授权后调用用户本机环境"的混合模式，此时 CLI 跑在用户自己的电脑上，属于第二讲的"本地长住房"范畴。

顺带一提，这恰恰说明**"第三方 CLI 的云端治理"是一块明确的行业空白**，也是潜在的产品机会点——但推动它的责任在平台侧，不在使用方。

> **一句话小结**：终端平台大门敞开；云端平台只给"网络服务式"的通道，没有给第三方 CLI 的门。飞书容器里的 CLI 是自家预装的特例，证明不了通例。

## 第五讲 · 瓶颈定性：钥匙在平台手里

**本讲要点**

- 第三方 CLI 要进入云端容器，平台必须同时给出三样东西：安装通道、持久化、用户权限/凭证注入。
- 这三样都是平台侧的架构决策，使用方单方面无法解决。
- "两层身份"必须分清：知道是谁 ≠ 持有凭证。

### 5.1 平台需要同时打开的"三扇门"

把第二、四讲的分析收拢，可以得到一张"条件清单"。第三方 CLI 想在云端平台正常工作，**以下三个条件缺一不可**：

| # | 条件 | 含义 | 由谁决定 |
|---|------|------|----------|
| ① | **安装通道** | 允许第三方可执行程序进入执行环境（自定义镜像、官方安装入口或 CLI 扩展机制） | 平台 |
| ② | **持久化** | 容器销毁后，工具本体和绑定关系还能保留，不必每次重装 | 平台 |
| ③ | **用户权限 / 凭证注入** | CLI 能以"当前对话员工"的身份合法调用企业系统，且凭证有安全的注入与托管机制 | 平台（+企业 IT 配合） |

现实是：三扇门的钥匙都在物业（平台）手里。这就是我们说"**瓶颈在平台侧，而不是我们的工具没做好**"的确切含义。

### 5.2 专门讲一讲"身份"：两层身份，绝不能混

云端智能体场景下，身份问题最容易被误解，值得专门讲清楚。这里存在**两层完全不同的身份**：

| 身份层 | 回答的问题 | 谁持有 | 智能体/容器看得到吗 |
|--------|------------|--------|---------------------|
| **应用/机器人身份** | 这个智能体"作为哪个应用"在运行 | 平台凭证中心托管 | 看不到凭证本身 |
| **终端用户身份** | 这次对话"是哪个员工在操作" | 平台在入口识别后注入上下文 | 看得到身份标识（姓名、工号等），但**没有对应的密码/令牌** |

由此产生两个必须纠正的常见误区：

**误区一："知道用户是谁，就能替用户调系统。"**

不是。"知道是张三在操作"只是一个**身份标识**；真正调用业务系统还需要张三的**凭证**（钥匙）。在飞书里能用用户身份调接口，是因为平台侧已经合法持有并托管了用户的授权令牌；换到自建业务系统，平台没有这个凭证，照样调不通。

**误区二："用户身份权限一定比机器人身份大。"**

不一定。用户身份的实际权限 =「应用申请到的权限」∩「该用户本人拥有的权限」，是交集关系。很多操作用机器人身份即可完成，不需要、也不应该冒充用户。

飞书侧已有的实践规范也值得我们借鉴（详见配套飞书调研）：读操作和普通写操作默认以用户身份执行（"所见即本人所见"）；会对外署名的动作（发消息、发评论）和自动化定时任务，一律以机器人身份执行（不能以员工名义自动发声）。

### 5.3 安全底线：身份必须走"可信通道"，不能经过模型的手

无论是 CLI 还是 MCP，有一条贯穿的安全原则：

> **用户身份与凭证必须由平台/基础设施层通过可信方式（签名、加密通道）下沉，智能体只能使用，不能修改、不能伪造、甚至不应看到原始凭证。**

飞书 lark-cli 的 Sidecar 设计（凭证留在容器外、签名代理）和 MCP 的标准安全模型（OAuth 2.1、凭证留在 Server 侧、模型不持有令牌），架构语言不同，原则完全一致。

行业层面更精细的"任务级短期凭证"标准也在推进中（如 IETF 的 AAuth 草案、Cloudflare 提出的智能体访问参考架构、Linux 基金会 AGNTCY 的安全运行时），但**这些都还在发展期，没有形成跨厂商统一、可以直接套用的成品**——这本身也是"瓶颈在平台侧、且平台侧自己也在摸索"的一个佐证。

> **一句话小结**：装得进、留得住、拿得到钥匙——三扇门都由平台控制。身份要分两层、凭证要走可信通道。我们能做的是把问题提清楚、把试点做扎实，而不是替平台去开门。

## 第六讲 · 我们已经有什么：saicmotor-cli 的家底

**本讲要点**

- saicmotor-cli 不是"一堆命令脚本"，而是一个"智能体可编排、能力可插拔、身份可接入"的平台化雏形。
- 已完成核心引擎、三个业务插件、SSO/OIDC 身份打通、内部 npm 分发与插件生态。
- 当前最实在的动作：在终端智能体上做试点，把身份体系做健全。

### 6.1 设计理念：让"加一个业务系统"不再需要改核心

我们自研 `@saicmotor/cli` 的起点，就是对标飞书 lark-cli 的架构思想，但面向公司自己的业务系统。它的核心设计是三层：

```
AI 智能体                           用户
   │                                 │
   ▼                                 ▼
 Skills（说明书：何时调、怎么编排）   命令行直接使用
   └──────────────┬──────────────────┘
                  ▼
             CLI 引擎（一套通用代码）
          ┌───────┴────────┐
     脚本覆盖（特殊逻辑）   HTTP 直连（按声明发请求）
                  ▼
             企业网关 → 各业务系统
```

关键在于：**引擎对所有业务系统用同一套代码，系统之间的差别只体现在一份"接口声明（catalog）"里。** 接入一个新系统，理论上只需新增声明和说明书，不动引擎。

### 6.2 已经建成的能力（截至 2026-09）

**平台骨架**

- CLI 核心引擎、认证框架、插件管理（TypeScript / Node ≥ 20）；
- 插件开发 SDK，业务团队可不接触核心代码开发新插件；
- 三个业务插件作为参考实现：**请假、考勤、用户信息**。

**身份体系**

- POC 阶段的账号密码登录；
- 已完成**飞书 OAuth/OIDC 对接的端到端验证**：员工用飞书身份登录，经网关换取各业务系统的访问令牌——与第五讲的"两层身份"模型对齐，SSO 只回答"你是谁"，各系统自己发"门票"；
- 凭证文件按 0600 权限保存，写操作有确认机制。

**分发与生态**

- 以 scoped 包（`@saicmotor/cli`）在**内部 npm registry** 分发，支持 `npx` 免安装运行；
- Skill 插件化：插件可独立安装、独立升级、独立版本号，具备插件与核心引擎的版本兼容校验（不兼容会被明确拦下，不拖垮运行）；
- 配套用户指南、插件开发者手册、一键卸载（不留残余）等工程化能力。

**验证环境**

- 同时建成了模拟网关（含飞书身份提供方、令牌交换）与模拟业务服务（请假/考勤），支持在不依赖真实生产系统的情况下做端到端验证；
- 各阶段均有自动化测试与人工验证手册。

### 6.3 现在能做的事：终端试点 + 身份健全

基于以上家底，在平台侧开门之前，有两件事是我们**现在就能做、且应该做实**的：

**第一件：在终端智能体上落地试点。**

CodeBuddy、Trae 这类智能体终端与 CLI 天然适配（第四讲），安装方式与普通 npm 包无异。建议选取小范围用户、围绕请假/考勤两个已有插件跑真实场景，验证：智能体仅凭 Skill 说明书能否正确编排多步操作；真实身份登录与令牌刷新是否顺畅；输出格式是否满足智能体稳定解析。

**第二件：把身份体系做健全。**

试点中同步完善：SSO 登录后的多系统令牌各自管理、独立过期与续期；用户身份与机器人身份的使用边界（参照飞书规范）；调用日志可审计。这部分工作**不依赖任何平台开放**，且无论将来桥接方式如何演进都能复用，是确定性的投资。

> **一句话小结**：我们手里不是一个试验性脚本，而是一个架构对标业界主流、身份与生态初具雏形的平台。当下最务实的动作，是终端试点做实、身份体系做全。

## 第七讲 · 下一步的两条工作线：先把事办成，再把边界讲明

**本讲要点**

- 不纠结"CLI 与 MCP 谁取代谁"，工作分成两条并行线。
- 线路一：在飞书、ADP 等云端平台上，**不拘泥于 CLI**，先尝试其原生的 MCP、Skill 方式，目标是业务先跑通。
- 线路二：CLI 在终端智能体上做技术试点；云端边界如实交代——平台开放之前，只支持终端。
- 附一份"需要平台方回答的问题清单"，作为推动开放的抓手。

### 7.1 为什么是"两条线"而不是"选一条路"

在云端平台装不进 CLI，并不等于"云端平台上什么都做不了"。平台各自提供了原生通道（MCP、Skill、插件、连接器）；而终端场景下 CLI 已经可用。因此与其在纸面上论证路线之争，不如把工作切成两条目标不同、互不拖累的并行线：

### 7.2 线路一：云端平台——不拘泥于 CLI，先用原生方式把事办成

**目标**：让"查请假、查考勤"这类业务能力在飞书智能体、腾讯 ADP 上先跑起来，工具形态服从平台规则。

**做法**：逐个平台验证其原生方式的可行性——

1. 该平台的 **MCP / Skill（技能）/ 插件能力能否承载我们的业务接口**？如何发布、审批、上架？
2. **终端用户身份如何获取和传递**？平台能注入哪些用户信息？业务系统侧能否据此完成鉴权？
3. 能接通哪些接口、粒度如何、限制是什么？

**产出**：每个平台一份可行性结论（能做/不能做/差什么条件），优先跑通 1–2 个真实业务场景。

**需要说明的定位**：这条线路上建设的 MCP/Skill 成果，是"为在该平台办事而穿的平台制服"，与 CLI 不是重复竞争，而是同一业务能力在不同环境下的不同形态。

### 7.3 线路二：CLI——终端试点做实，云端边界如实交代

**目标**：把 saicmotor-cli 在终端智能体上的价值用真实试点证明；同时对其能力边界给出不含糊的交代。

**做法**：

1. 在 CodeBuddy、Trae 等终端智能体上开展小范围试点（见第 6.3 节）；
2. **边界如实说明**：在平台开放"安装通道、持久化、凭证注入"三条件（第五讲）之前，**CLI 只支持终端类智能体，无法进入飞书、ADP 这类云端容器**。这是行业现状决定的边界，不是产品缺陷，也不应由我们承诺"很快就能支持"。
3. 持续关注行业动向（云端平台与本机执行合流、第一方 CLI 生态、相关标准进展），一旦某个平台开放扩展能力，第一时间接入。

### 7.4 两条线路对照

| 维度 | 线路一：云端原生方式 | 线路二：CLI 终端试点 |
|------|----------------------|----------------------|
| 目标 | 业务在云端平台先跑通 | 验证并坐实 CLI 的价值 |
| 平台 | 飞书、ADP 等 | CodeBuddy、Trae 等终端智能体 |
| 方式 | MCP / Skill / 插件（平台原生） | saicmotor-cli（子进程调用） |
| 身份 | 依赖平台注入，需逐平台确认 | SSO/OIDC，我们自控 |
| 当前状态 | 待可行性验证 | 雏形具备，可试点 |
| 下一步 | 出分平台可行性结论 | 小范围真实场景试点 |
| 风险/边界 | 受平台规则约束 | 云端平台暂不支持，边界已明确 |

### 7.5 需要平台方回答的问题清单

无论从哪条线路推进，以下问题都需要平台侧（或通过商务渠道）给出明确答复。建议作为正式问题提出，并留存答复：

1. 平台是否允许第三方程序（CLI/自定义二进制）安装进执行环境？通过什么机制（自定义镜像、官方扩展入口）？
2. 执行环境中哪些目录可以跨会话持久化？工具和配置能否长期保留？
3. 平台能否向第三方工具/MCP Server 安全传递终端用户身份？以什么格式、是否带签名、能否防伪造？
4. 平台是否托管用户对第三方应用的授权（如 OAuth 授权流程）？凭证的生命周期如何管理？
5. 对外部系统调用的审计日志、限流、权限裁剪，平台提供哪些能力？
6. 平台在"云端环境调用用户本机资源"方向上的路线图是怎样的？

这份清单同时也是判断"平台门什么时候开、开了多大"的标尺。

> **一句话小结**：云端平台上先按它的规矩把事办成；终端场景下把 CLI 的试点和价值做出来，边界讲到明处。平台的门何时开，用问题清单去推动、去度量。

## 结课 · 一页总结

如果今天只能记住一页，请记住这一页：

**1. 现状：三条桥，两种房间。**
智能体连接企业系统有三种方式——CLI（驻场办事）、MCP（标准总台）、Skills（操作手册）。后两者是当今主流，AI 原生 CLI 是被各大厂验证的新趋势。智能体则有两种运行环境：本地长住房（终端智能体）与云端酒店房间（平台托管智能体）。

**2. 边界：CLI 必须与智能体同住；云端的门，钥匙在平台手里。**
终端智能体上，CLI 现在就能装、就能用。云端平台上，第三方 CLI 要工作，平台必须同时给出安装通道、持久化、凭证注入三个条件；截至今天，没有任何主流平台开放这些能力。飞书容器里的 lark-cli 是"自家预装、代管钥匙"的特例，不是通例。

**3. 行动：两条线并行。**
线路一：在飞书、ADP 等平台上不拘泥于 CLI，先用原生 MCP/Skill 验证业务可行性。线路二：把 saicmotor-cli 在 CodeBuddy、Trae 等终端智能体上做实试点，同步健全 SSO 身份体系。我们的 saicmotor-cli 已具备引擎、业务插件、身份打通、内部分发与插件生态的完整雏形——工具已经在手，差的是平台开门的时机。

### 附录 A · 名词术语表

| 术语 | 通俗解释 |
|------|----------|
| API（接口） | 业务系统对外提供的"办事窗口"，程序通过它查询或提交数据 |
| CLI（命令行工具） | 用文字命令操作的程序；智能体通过子进程方式调用它 |
| 容器 / 沙箱 | 程序运行的隔离"房间"；云端容器通常临时分配、用完销毁 |
| 子进程 | 一个程序在运行中"喊"另一个程序替它干活的操作系统机制；二者必须同处一个环境 |
| MCP | 模型上下文协议，智能体发现与调用外部工具的行业标准（2024-11 由 Anthropic 开源，现属 Linux 基金会） |
| MCP Server | 业务系统一侧按 MCP 标准提供的服务；凭证保存在此，不进入智能体环境 |
| Skills（技能） | 教智能体怎么办事的说明书（SKILL.md）及配套脚本；按需加载 |
| SSO | 单点登录，企业统一身份认证：登录一次，多个系统认你 |
| OAuth / OIDC | 常见的安全授权协议/身份协议：用户授权后，由平台代为持有访问凭证 |
| Token（令牌） | 系统发给已认证用户的"临时门票"，有有效期、可独立刷新 |
| 应用/机器人身份 vs 终端用户身份 | 前者是"智能体作为哪个应用运行"，后者是"这次是哪个员工在操作"；两层不可混 |
| Sidecar（侧车） | 凭证留在智能体环境之外、由可信代理代持并代为调用的安全模式 |
| Agent Harness / Claw | 平台对"云端托管运行底座/云端工作空间"的产品化称呼（腾讯、字节均有类似形态） |

### 附录 B · 平台调研要点速查

- **终端类（CLI 可用）**：Claude Code、Trae/TraeCode CLI、CodeBuddy Code、Gemini CLI、Cursor、Windsurf。共性：运行在用户本地，Shell/Bash 工具以子进程执行命令，支持权限规则与沙箱，npm 安装为主。
- **云端托管（第三方 CLI 无入口）**：腾讯 ADP（Skills/连接器/工作流）、Coze（插件/工作流/MCP；其 `@coze/cli` 是本地客户端）、飞书 Aily（技能/MCP/工作流；第一方 lark-cli 官方注入、凭证侧车托管）、阿里百炼、文心智能体、OpenAI（Actions/MCP/连接器）。
- **私有化部署**：Dify 等开源平台可自行改造镜像、预装任意 CLI——自由来自自托管。

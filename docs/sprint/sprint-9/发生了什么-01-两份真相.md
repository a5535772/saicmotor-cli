> **修复编号：C1** | **严重度：🟡** | **改前分支：master@453a827** | **改后：Sprint 9**

## 认识这个 bug：两份一模一样的代码，但分开了

看下面两份文件：

```
packages/sdk/src/catalog-types.ts   ← 一份
packages/cli/src/schema/catalog.ts  ← 另一份，内容相同
```

`catalog-types.ts` 是给插件开发者用的——他们在写 `saicmotor.plugin.json` 时需要知道 `Service`、`Method`、`Field` 这些类型的结构，所以 SDK 导出它们。`catalog.ts` 在 CLI 侧被引擎消费——加载核心 catalog、校验插件传来的 catalog、执行脚本时传入 `ScriptContext`。

两份文件从 zod schema 的定义，到 `z.infer<typeof XXXSchema>` 生成的类型，**逐字相同**。但这不意味着它们「等同」——它们只是两个独立的副本，只是恰好在格林尼治时间 2026-09-30 之前还没有发生分歧。

## 原理：单一真相源

软件工程有一条被反复验证但永远被低估的原则——**DRY 其实不是"别写重复代码"**。

DRY 是别让同一份**知识**有两个容器。两份代码同一时段内容相同，不等于它们不会发生分歧——事实上，**正是「同一时段内容相同」麻痹了所有维护者**，让人以为"已经在 SDK 里定义过了"，然后在其中一份上改完就交差。

在 saicmotor-cli 里，这个分歧已经有两个苗头：

1. SDK 里叫 `catalog-types.ts`，CLI 里叫 `catalog.ts`——名字不同，新人不知道它们是对应的。
2. CLI 里直接 import 了 `zod` 来写 `FieldSchema`/`MethodSchema`/`ResourceSchema`/`ServiceSchema`——而 SDK 是包，它当然也得依赖 `zod`。现在 `zod` 同时出现在两个 `package.json` 的 `dependencies` 里。如果有一天 CLI 和 SDK 各自升了不同的 `zod` 版本，`z.infer` 给你的是两种不同的类型，TypeScript 编译不过——但最可怕的是，在 workspace link 模式（`npm workspaces` 把所有包都 link 到 root `node_modules`）下你不会发现这个问题，它只会在 **published 安装**时暴露。

这就是 DRY 真正的价值：不是"少打几个字"，而是**消除可以独立漂移的观点**。

## 代码改造

### Step 1：把 schema 搬家到 SDK

SDK 是唯一有资格对外发誓的包——插件开发者只 `import @saicmotor/sdk`，所以类型契约的唯一源头必须是 SDK。改造的过程是用 `git mv` 移动：

```
packages/cli/src/schema/catalog.ts → packages/sdk/src/catalog.ts
```

`git mv` 保留了文件的 git 历史——历史的 blame 不会断。同时删除旧的 `packages/sdk/src/catalog-types.ts`（它之前只包含类型别名，zod schema 不在它身上）。

改造前——CLI 本地有一套完整的 schema：

```ts
// packages/cli/src/schema/catalog.ts（改造前）
import { z } from "zod";

export const FieldSchema = z.object({ /* ... */ });
export const MethodSchema = z.object({ /* ... */ });
export const ResourceSchema = z.object({ /* ... */ });
export const ServiceSchema = z.object({ /* ... */ });

export type Field = z.infer<typeof FieldSchema>;
export type Method = z.infer<typeof MethodSchema>;
export type Resource = z.infer<typeof ResourceSchema>;
export type Service = z.infer<typeof ServiceSchema>;
```

改造后——同一份文件搬到了 SDK：

```ts
// packages/sdk/src/catalog.ts（改造后）
// 内容逐字相同，只是文件位置变了
import { z } from "zod";

export const FieldSchema = z.object({ /* ... */ });
// ...
export type Service = z.infer<typeof ServiceSchema>;
```

SDK 的 `index.ts` 伴随更新：

```diff
- export { FieldSchema, MethodSchema, ResourceSchema, ServiceSchema } from "./catalog-types";
- export type { Field, Method, Resource, Service } from "./catalog-types";
+ export { FieldSchema, MethodSchema, ResourceSchema, ServiceSchema } from "./catalog";
+ export type { Field, Method, Resource, Service } from "./catalog";
```

### Step 2：CLI 不再有"自己的"catalog 类型

CLI 里的 8 个引用点全部改指 `@saicmotor/sdk`：

```diff
// packages/cli/src/engine/script.ts（改造前）
- import type { Service, Method } from "../schema/catalog";

// packages/cli/src/engine/script.ts（改造后）
+ import type { Service, Method } from "@saicmotor/sdk";
```

### Step 3：context.ts 也改指新家

SDK 自己的 `context.ts` 之前引的是旧的 `./catalog-types`：

```diff
// packages/sdk/src/context.ts（改造前）
- import type { Service, Method } from "./catalog-types";

// packages/sdk/src/context.ts（改造后）
+ import type { Service, Method } from "./catalog";
```

## 这一讲的核心知识点

**两份代码同一时段内容相同 ≠ 它们不会发生分歧。** 视觉等价不是结构等价——有独立审计能力的时间会证明这一点。

**类型在哪里倒出，就在哪里定义。** 如果一个类型是从包 A 导出的——即它是 A 的公共 API 合约——那么它的定义文件也必须住在 A 里。B 用 A 的类型，OK；B 自己维护一份 A 类型的副本，只是假设它跟 A 同步，迟早要炸。

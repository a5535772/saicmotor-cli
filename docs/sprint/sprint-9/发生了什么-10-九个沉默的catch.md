# 发生了什么 · 第十讲：九个沉默的 catch——当异常处理选择不发一语

> **修复编号：C5** | **严重度：🟡** | **改前分支：master@453a827**

---

## 认识这个 bug

在整个 CLI 代码库中，有 9 个 catch 块长这样：

```ts
try {
  // 做一些可能失败的事
} catch {
  // （空行，或一行含糊的注释）
}
```

分布在 6 个文件中：

| 文件 | 数量 | 场景 |
|------|------|------|
| `config/config.ts` | 1 | 配置文件读取失败 |
| `engine/state.ts` | 1 | 状态文件损坏 |
| `plugin/registrar.ts` | 1 | 插件注册清理失败 |
| `plugin/loader.ts` | 4 | 各类插件加载降级路径 |
| `cli/plugin-cmds.ts` | 1 | 插件列表命令的辅助操作 |
| `cli/catalog.ts` | 1 | catalog 发现错误 |

这些 catch 块都有一个共同点：**它们确实需要 catch 这个错误——但没有人知道为什么。** 

看一个典型场景：`plugin/loader.ts` 里加载插件时如果某个目录读失败——这个 catch 是「有意为之」还是「临时写了 try 后来忘了回来实现」？读者无法区分。

这就是沉默 catch 的核心问题：**每个 catch 是一个决策——"这个错误我不处理"——但这个决策的原因没有记录在任何地方。** 下一个维护者必须猜——是 bug 还是特性？

## 原理：catch 的两个责任

一个 `try/catch` 块实际上有两个责任——但大多数人只想到了第一个：

| 责任 | 说明 | 完成的信号 |
|------|------|-----------|
| **故障遏制** | 阻止错误传播到调用栈的更上层 | catch 块的存在本身就是这个信号 |
| **故障文档** | 说明为什么这个错误在这里被遏制，以及遏制后的系统状态 | **注释里写上理由**是唯一的信号 |

看一个对比：

```ts
// ❌ 故障遏制完成，故障文档缺失
try {
  const raw = fs.readFileSync(configPath, "utf-8");
  return parse(raw);
} catch {
  return {};
}

// ✅ 两个责任都完成
try {
  const raw = fs.readFileSync(configPath, "utf-8");
  return parse(raw);
} catch {
  // 配置文件缺失或损坏时降级为空配置——用户首次安装时 config 文件尚未创建，
  // CLI 需在此场景下可以正常启动（后续 login/init 命令负责创建文件）
  return {};
}
```

第一个版本在行为上和第二个版本完全一样——两份代码在运行时做的事一模一样。但第一个版本对于下一个维护者是一个谜：ta 必须反推「为什么这里返回 `{}`？」——这个反推需要理解首次安装的时序、CLI 启动需要的降水量、以及为什么这个错误不能传播。**这不是代码的逻辑错误——这是知识的消失。**

## 代码改造

每个 catch 块补上了两样东西：

1. **为什么错误是可以被忽略的**——解释这个错误代表什么合法/预期的降级场景。
2. **降级后的系统状态**——说明 catch 之后程序处于什么状态，是否仍能满足调用方的契约。

具体到每个文件：

### config.ts

```diff
  } catch {
+   // 配置文件缺失或 JSON 损坏——首次安装时 config 文件尚未创建，降级为空配置
    return {};
  }
```

### state.ts

```diff
  } catch {
+   // 状态文件缺失或损坏——作用域销毁操作是幂等的，丢失状态文件等同于"不存在"，无副作用
  }
```

### registrar.ts

```diff
  } catch {
+   // 插件路径的符号链接删除失败——可能已被用户手动删除或权限不足，不影响 CLI 功能
  }
```

### loader.ts（4 处）

```diff
  } catch {
+   // 插件目录下的非目录文件（如 README.md）——readdir 返回的所有条目里跳过非目录项
    continue;
  }
```

```diff
  } catch {
+   // manifest.json 缺失、不合法的 JSON 或 schema 不匹配——跳过此插件，由 validateManifest 的调用方统一警告
    continue;
  }
```

```diff
  } catch {
+   // 单个 catalog 文件损坏不阻断其他 service 加载——错误已在 loadPluginServices 内部 push 到 warnings channel
    continue;
  }
```

```diff
  } catch {
+   // scripts 目录缺失（插件未提供脚本）——脚本目录非强制，无 scripts 的插件仅提供 API 注册
  }
```

### plugin-cmds.ts

```diff
  } catch {
+   // 插件列表展示时读取特定插件元数据失败——单个插件的元数据缺损不影响其他插件的列表展示
  }
```

### catalog.ts

```diff
  } catch {
+   // catalog 发现过程中某个文件不合法——不阻断其他文件的发现，错误已在上层汇总
  }
```

## 这一讲的核心知识点

**一个空的 catch 块不是"我处理了这个错误"——它是"我决定不处理但没记录决策"。** 而「没记录」意味着这个决定在三个月后不可审计——如果那段 catch 后来被发现掩盖了一个值得响应的错误，没人知道当初为什么要掩盖它。

这引出一个实践原则：

> `catch {}` （字面意义的空大括号）不应出现在任何生产代码中。至少要有注释。最好至少有注释——如果降级路径足够复杂，应该提取为命名函数来描述语义。

这 9 个 catch 的修复不涉及任何逻辑变化——所有测试在改前改后完全一致。但它回答了"为什么这里允许失败"——这个答案让维护者免于一次因果考古。

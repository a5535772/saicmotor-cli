# 发生了什么 · 第二讲：太宽的契约

> **修复编号：A7** | **严重度：🟢** | **改前分支：master@453a827**

---

## 认识这个 bug：一份默许的"全部都能看"

打开改造前的 `@saicmotor/sdk`，它导出的 `Config` 类型长这样：

```ts
export interface AuthConfig {
  type: "password" | "exchange";
  loginPath: string;
  tokenPath: string;
  tokenHeader: string;
  tokenPrefix: string;
  startPath: string;
  exchangePath: string;
  loopbackHost: string;
  loopbackPort: number;
  callbackTimeoutMs: number;
}

export interface Config {
  gateway: string;
  auth: AuthConfig;
}
```

`Config` 有 11 个字段。`AuthConfig` 有 10 个——包括 OAuth 回调端口、飞书 SSO 路径、token 请求头前缀这些**只跟认证引擎有关**的字段。

这 11 个字段，插件脚本能用几个？

**一个。** 就 `gateway`。插件只需要知道「网关地址」，拼出完整的 `/api/leave/applications/submit` 之类的 URL。`auth` 及其下的 10 个子字段，对插件脚本来说**毫无意义**——插件根本不该知道 CLI 是用飞书 SSO 登录还是密码登录，更不该看到回调端口和 token 头前缀。

## 原理：接口隔离

我们学过面向对象设计的「接口隔离原则」（ISP）：客户端不应该被迫依赖它不需要的接口。

但这条原则不止适用于面向对象。**在包 API 设计上，它是同一个道理：一个包的公共类型有多宽，就意味着它的消费者被强制阅读多少元信息。** 宽类型有三重代价：

**1. 编译期：** 类型声明把内部结构暴露给了所有 `import type { Config } from "@saicmotor/sdk"` 的人。插件脚本作者可以在 `ctx.config.auth.loopbackPort` 上得到一个 TS 自动补全提示——这本身不是 bug，但它是一个信号：这个字段不该在这个作用域里可访问。

**2. 维护期：** 当你重构 CLI 的认证层——比如把 `loopbackPort` 从配置移到环境变量——你必须假设某个插件已经读了它。只要 `AuthConfig` 还在公共 API 上，任何字段的删除或改名都是 breaking change。

**3. 认知负荷：** 一个新插件作者打开 `Config` 类型，看到 10 个 `auth.*` 字段，他会以为"这些是我可以用的"。但实际上 `auth` 在插件脚本的运行时上下文里**根本不提供**（`run.ts` 构造 `ScriptContext` 时不会填入 auth 字段）——类型说可以，运行时说不行。这就是「契约」与「实现」之间的裂缝。

## 代码改造

### SDK 侧：只暴露插件需要的

```diff
- export interface AuthConfig {
-   type: "password" | "exchange";
-   loginPath: string;
-   tokenPath: string;
-   tokenHeader: string;
-   tokenPrefix: string;
-   startPath: string;
-   exchangePath: string;
-   loopbackHost: string;
-   loopbackPort: number;
-   callbackTimeoutMs: number;
- }
-
- export interface Config {
-   gateway: string;
-   auth: AuthConfig;
- }
+ /** 插件脚本可见的配置子集。CLI 侧持有完整的 Config（含 auth），运行时构造 ScriptContext 时窄化为本类型。 */
+ export interface Config {
+   gateway: string;
+ }
```

**关键设计决定：** 不删 CLI 自己的完整 `Config`。

CLI 内部仍需要一个含 `auth` 的 `Config`——它在启动时加载配置文件、创建认证提供者、传入 `runMethod`。改造前，CLI 和 SDK 有两份 `Config` 定义（都在说自己）；改造后，SDK 的是窄版本（只有 `gateway`），CLI 的是宽版本（含 `auth`），两者都是正确的——一个对插件发誓，一个对引擎发誓。

### CLI 侧：类型可赋值性

`run.ts` 里构造 `ScriptContext` 时，传给 `executeScript` 的 `config` 字段取自 CLI 的完整 `Config` 对象：

```ts
// packages/cli/src/engine/run.ts（改造后）
const ctx: ScriptContext = {
  config,           // CLI 全量 Config → 赋值给 SDK 窄 Config { gateway: string }
  service: methodRoute.service,
  method: methodRoute.method,
  values: overrides?.values ?? {},
  dryRun: overrides?.dryRun ?? false,
  ensureToken: async () => { /* ... */ },
};
```

TypeScript 的结构类型系统在这里表现得像鸭子类型：CLI 的 `Config`（含 `{ gateway, auth }`）可以赋给 SDK 的 `Config`（仅 `{ gateway }`）——因为前者包含后者所需的所有字段。这是 `&` 赋值而非字面量赋值，所以超额属性不被拒绝。

换句话说，CLI 在运行时会传一个含 `auth` 的对象进去，但插件脚本**通过类型系统看不见** `auth` 字段——`ctx.config.gateway` 有类型提示，`ctx.config.auth` 报编译错误。

## 这一讲的核心知识点

**公共类型不是"内部配置的镜像"——它就是插件的权限边界。** SDK 给插件暴露的每一个字段，都是在告诉插件开发者「这是你可以依赖的，我们承诺未来版本也保有它」。剩下的字段——不管内部实现用不用——都不应该出现在这个接口上。你会为你暴露的每个字段承担一个**永久维护契约**——它的删除或改名就是一个 breaking change。窄契约是善意，宽契约是炸弹。

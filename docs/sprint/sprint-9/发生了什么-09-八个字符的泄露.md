# 发生了什么 · 第九讲：八个字符的泄露——当 JWT 前缀出现在了终端上

> **修复编号：S5** | **严重度：🟡** | **改前分支：master@453a827**

---

## 认识这个 bug

飞书 SSO 登录成功后的消息是：

```
已登录，token 已缓存（eyJhbGci…）
```

括号里的 `eyJhbGci…` 是什么？它是 JWT token 的前 8 个字符。

看改造前的代码：

```ts
const token = await login();
console.log(`已登录，token 已缓存（${token.slice(0, 8)}…）`);
```

这个 `console.log` 的意图很直白——给用户一个「有什么东西被写入了」的可见信号。开发者选择 `.slice(0, 8)` 作为"提供一个可辨认的前缀但不透露整个 token"的平衡。

但 `eyJhbGci` 这六个字符不是随机 base64——它是每一个标准 JWT header 的开头：

```
eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9
= base64decode →
{"alg":"RS256","typ":"JWT"}
```

这意味着任何看到终端输出的人能立刻确认两件事：

1. **这是一个 JWT。** `eyJ` 是 `{"` 的 base64 前缀，`eyJhbGci` 解码后是 `{"alg"`——这是每个 JWT 的第一段必然内容。
2. **JWT 的签名算法是 HS256/RS256/ES256。** 如果后续字符泄露了 `alg` 字段的完整值，攻击者就知道了签名算法。

单独 8 个字符的 base64 前缀不足以伪造 token——但这 8 个字符确认了 token 的**存在**和**格式**。在安全领域叫"信息泄露"（information disclosure）：攻击者现在知道：
- 系统使用 JWT 认证
- token 在终端可见（意味着使用者的屏幕截图、CI 日志、会议录屏都可能记录这 8 个字符）

## 原理：token 前缀 ≠ 安全 token

常见的一个误解是"token 前缀是安全的"——很多服务会在 UI 里显示 `ghp_xxxx...`（GitHub）或 `sk-xxxx...`（OpenAI）作为 token 的认清标识。但这些服务显示的是**专门设计的前缀**（`ghp_`、`sk-`）——它们是固定的、公开已知的 magic string，不是从 token 本体截取的。

JWT 没有这样的固定前缀——它由三个 base64url 段以 `.` 连接而成。截取前 8 个字符恰好落在了 header 段上，而 header 是**标准化的、可预测的内容**。`eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9` 的 base64 编码前 8 个字符永远是 `eyJhbGci`（至少对于使用标准 JWT 库的系统而言）。

所以 `.slice(0, 8)` 不但提供了可辨认性——它提供了**可被辨认的信息类型**。

## 代码改造

只有两行变化。先看改前改后的对比：

```diff
- const token = await login();
- console.log(`已登录，token 已缓存（${token.slice(0, 8)}…）`);
+ await login();
+ console.log("已登录，token 已缓存");
```

变化只有两点：

1. **`const token =` 被移除。** 因为 `token` 变量没有被后续代码消费——它的唯一目的是被 slice 并打印。一旦不再打印，这个变量绑定就不需要了。
2. **token 前缀信息从用户可见输出中完全移除。** 终端上现在只有「已登录，token 已缓存」——告知用户结果但不透露 token 的任何部分。

这是整个 Sprint 9 中最小的 diff——删 1 行、改 1 行——但也是安全影响最大的修改之一。

## 这一讲的核心知识点

**token 的任何一部分出现在终端上就是信息泄露——即使只有 8 个字符。** 安全边界不在字符数上，在「字符本身携带的信息」上。JWT 的 header 是结构化的公开知识——所有人都知道 `{"alg":"..."}` 会 base64 成什么——所以把 header 的 base64 前缀给到可见输出，等于对攻击者说"我们用 JWT"。

关于这个 fix 的深层设计原则：

1. **「可辨认的前缀」≠「安全的前缀」。** 截断不是安全机制——它只是把完整信息变成部分信息。如果那部分恰好指向整个消息的类型和格式，截断就是坏的实践。

2. **终端输出是永久记录。** `console.log` 的输出不是扔给用户的临时弹窗——它会进入终端 buffer、CI 日志、`screen`/`tmux` 的 scrollback、SSH session 的 audit log 等等。任何一个副本的泄露都可能暴露 token 前缀——即使原始用户早就关了终端。

3. **如果信息不对用户有操作性价值，就不应该出现在用户可感知的输出里。** token 前 8 个字符对用户有什么可做出的操作？答案是"零"。用户不能基于这 8 个字符决定去做什么——它只是让用户看到些东西。这是多余的信号。

> 删掉一行代码的安全加固往往比加十行代码的防御更可靠——因为它不是用更多复杂性去对抗攻击面，而是直接收回了那部分攻击面。

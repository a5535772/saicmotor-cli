# 发生了什么 · 第八讲：一个没人用的参数——当"以备后用"变成了永恒的摆设

> **修复编号：A1** | **严重度：🟢** | **改前分支：master@453a827**

---

## 认识这个 bug

`loadPlugins()` 是 CLI 启动流程中最核心的函数之一——它发现、加载并返回所有已安装插件的 services。改造前它的签名是：

```ts
async function loadPlugins(config: Config): Promise<LoadedPlugin[]> {
```

这个 `config: Config` 参数——一个包含 `gateway` 字段的对象——看起来很重要：load plugins 的时候可能需要 config 里的什么东西。但当你读到函数体的第一行：

```ts
async function loadPlugins(config: Config): Promise<LoadedPlugin[]> {
  // ... 遍历插件目录 ...
  // ... 读 manifest ...
  // ... 加载 services ...
  // ... 处理冲突 ...
  //                     ← 全函数 80+ 行，没有一行提到 config
}
```

**一个都没有。** `config` 参数被声明、被接收、但从未被读取。三个调用站点却都在传它：

```ts
// cli/index.ts
const plugins = await loadPlugins(config);

// cli/plugin-cmds.ts
const plugins = await loadPlugins(loadConfig());

// plugin/suite.ts
this.plugins = await loadPlugins(loadConfig());
```

每个站点要么自己调 `loadConfig()` 造一个 config 传进去，要么从外层接收 config 再传——三处调用都做着完全相同的事：**传一个函数永远不会读的参数。**

`loadConfig()` 本身承担真正的 I/O——读文件、parse YAML——虽然内容很小，但这意味着每次 CLI 启动（安装插件、执行应用、运行测试），`loadConfig` 都在耗一个文件读加 YAML parse 的开销。但这不是性能故事——这是「为什么有这个开销？」的故事。

## 原理：隐式依赖转向

这个参数不是一开始就是死的。它是**逐渐变成死参数的**——当 `loadPlugins` 被重构为不需要 config 时，调用方没跟着清理。

追溯历史：

1. 某个时刻，`loadPlugins` 确实读了 `config` 里的某些字段——可能用它来过滤插件、决定搜索路径、配置加载策略。
2. 重构时这些逻辑被移走了（也许去了 `Suite` 层、也许被简化掉），但参数签名留了下来。
3. TypeScript 没报错——因为类型是对的，只是值没被读。`noUnusedParameters` 是 `tsconfig` 里的一个独立 flag，而这个项目没开它。
4. 三处调用站点继续 `loadPlugins(loadConfig())`——没人问"我们传了它，但 `loadPlugins` 内部用了没？"

这叫做**"隐式依赖转向"**：当一个参数从"需要"变成"不需要"的过程中，没有任何编译信号通知调用方，调用方继续维护着一段没人要的传递链：

```
main() → loadConfig() → config  →  loadPlugins(config)  →  (丢弃)
                              └→  Suite(config)          →  其他使用（这个是真的）
```

`config` 在 `Suite` 和其他地方确实被使用了——问题只是 `loadPlugins` 的签名说"我需要它"但实际上不需要。

## 代码改造

### Step 1：去参数化

```diff
-async function loadPlugins(config: Config): Promise<LoadedPlugin[]> {
+async function loadPlugins(): Promise<LoadedPlugin[]> {
```

函数内部没有任何逻辑变化——因为本来就不读这个参数。

### Step 2：清理三处调用站点

```diff
// cli/index.ts
- const plugins = await loadPlugins(config);
+ const plugins = await loadPlugins();

// cli/plugin-cmds.ts
- const plugins = await loadPlugins(loadConfig());
+ const plugins = await loadPlugins();
- import { loadConfig } from "../config/config";
+ // loadConfig import removed (no longer needed here)

// plugin/suite.ts
- this.plugins = await loadPlugins(loadConfig());
+ this.plugins = await loadPlugins();
- import { loadConfig } from "../config/config";
+ // loadConfig import removed
```

每处调用变成无参数调用，同时删掉不再需要的 `loadConfig` import。

### Step 3：验证

测试套件确认插件加载行为一致——警告仍然产生、service 列表仍然返回、冲突检测仍然生效。唯一的变化是启动路径短了一步：少了一次 `loadConfig()` 调用。

## 这一讲的核心知识点

**签名是契约，不是建议。** 当你说 `function f(x: T)`，你向所有调用方宣布：「调用我时需要提供一个 `T`」。如果 `T` 不被读取——也就是参数的 name 永远不出现在函数体里——那这个声明不是说谎，但更糟：它是过期的断言，不可检测。

TypeScript/C 里与此等价的 `-Wunused-parameter` 编译器 flag 会抓住它——但在 TypeScript 生态里，很多人关掉它（或没开），因为它会在你在意它之前发出太多噪音（interface 实现、callback 签名）。但这正是为什么 **dead parameter 特别阴险**——它是一个根本没有任何意义的通知的「声明依赖」。

修复它的操作本身极其廉价——删掉、清理各个调用方、测试确认无任何变化——但发现的成本高。只有读代码的人（不是机器、不是 TypeScript、不是 linter）才能看到「这里有三个文件在费力传一个没用到的对象」。

> 一个没人读的参数不是轻量债——它是一条活跃的误导信息。它让维护者以为"这个函数需要外部输入"，而实际不需要。当未来的修改者基于这条信息做设计决策时，就会发现自己是根据一个不对的假设在做判断。

这种修复有一个比较范式化的检查法：**被你的函数签名提到的任何类型，如果函数体里不出现对应变量——你都欠它一个删除或一个解释。**

# 发生了什么 · 第七讲：一个被静默丢弃的坏 catalog 文件——当降级选择沉默

> **修复编号：C3** | **严重度：🟡** | **改前分支：master@453a827**

---

## 认识这个 bug

插件 `@saicmotor/plugin-leave` 的 `catalog/services/` 目录下有两份 JSON 文件：

```
catalog/services/
├── leave-services.json   ← 正常的 service 定义
└── corrupted.json        ← 某个字段的类型不对
```

`loadPluginServices` 会遍历这个目录，对每一个 `*.json` 做 `ServiceSchema.parse(raw)`。改造前的逻辑是：在 per-file 的 try/catch 里，如果 parse 抛了，catch 块的注释说：

```ts
// 此处暂不 push（loadPluginServices 无 warnings channel），后续重构时统一传递
```

然后 **`continue`——这个文件名再也不被提起。**

发生了什么：

1. `corrupted.json` 被 parse，`ZodError` 抛出。
2. catch 块捕获，吞掉——不 push warning，不写日志，不改变任何返回值。
3. `leave-services.json` 正常加载。
4. CLI 启动成功，只有 `leave-services` 定义的 APIs 在工作。

用户永远不会知道 `corrupted.json` 被忽略了。过几个月插件的作者改了 `leave-services.json`，预期行为应是"旧的 corrupted file 不再工作所以被自动丢弃"——但作者不知道它**从来没工作过**，因为 CLI 从来没出声。

## 原理：降级必须可见

系统设计中经常有降级——当一份文件损坏、一个后端不可用时，系统给它忽略以待后续处理。这是一个正确的容错策略。但有一个边线原则：

> **每一次降级都应该产生一条可检索的信号。**

这可以是 warnings 列表、log 行、metrics counter——任何在外界可见的东西。但绝不能是**内部静默 catch**。为什么？

- **静默意味着零可追踪维修费用。** 如果错误发出信号，运营者知道检查此事并将一行修复插入 backlog。但如果它不出声，错误变成真正的「系统默认」——下次教训可能是从生产事故开始。
- **静默让降级变得不可审计。** 未来某天一个服务停止响应，操作员会疑问"是因为这个 catalog 文件坏了吗？"——如果日志里没有任何关于这个文件的 entry，答案是「未知」。

## 代码改造

### Step 1：给 `loadPluginServices` 一个 warnings 通道

改造前，这个函数的返回类型是 `Service[]`——只返回「加载成功的 service 列表」：

```ts
function loadPluginServices(pkgRoot: string, manifest: PluginManifest): Service[] {
```

改造后，返回值变成了一个对象，包含两个数组：

```ts
function loadPluginServices(
  pkgRoot: string,
  manifest: PluginManifest,
): { services: Service[]; warnings: string[] } {
  const services: Service[] = [];
  const warnings: string[] = [];
  // ...
  return { services, warnings };
}
```

### Step 2：把警告从 catch 里推出去

```diff
  } catch (e: unknown) {
-   // 此处暂不 push（loadPluginServices 无 warnings channel），后续重构时统一传递
+   // 单个 catalog 文件损坏不阻断其他 service，汇总 warning 返回给调用方
+   warnings.push(`插件 ${manifest.name} catalog 校验失败 (${file}): ${(e as Error).message}`);
  }
```

注意这个警告包含三项信息：插件名、文件名、实际错误信息。这给插件开发者提供了**即时修复所需的全部信息**。

### Step 3：调用方把 warnings 汇入自己的 channel

`loadPlugins` 里从 `loadPluginServices` 取返回值时，把 warnings 合并到自己已有的 `warnings` 数组：

```diff
- const services = loadPluginServices(pkgRoot, manifest);
+ const { services, warnings: svcWarnings } = loadPluginServices(pkgRoot, manifest);
+ warnings.push(...svcWarnings);
```

这样 warnings 的链路就通了：`loadPluginServices` → `loadPlugins` → `main()`。

### Step 4：测试确认「有警告」

原来的测试名叫 `"skips bad catalog JSON silently"`——名字本身就是 bug 的陈述。"silently" 正是我们要修的问题。

改造后测试追加断言：

```ts
expect(
  result.warnings.some(
    (w: string) => w.includes("校验失败") || w.includes("解析失败"),
  ),
).toBe(true);
```

这意味着：**测试不仅确认 "文件被跳过"，现在还认证 "跳过这件事被沟通了"。** 测试名也改为 `"skips bad catalog JSON with a warning"`——因为静默不是功能，是缺陷。

## 这一讲的核心知识点

**错误是事件——它被观察到的通道越多，修复它的概率越大。** 在这个设计里，单个损坏的 catalog 文件不能阻止整个插件加载，这是正确的降级决策。但降级发生的位置必须有一条路径让信息上升到可见层——否则就成了无声瓦解：

> 降级本身不可见时，「容错」就不是容错——它是「让系统带着隐藏损伤继续前进」。

这原则不只针对插件：你在任何地方 catch 了一个错误且选择不重抛时，问自己一个纯实践问题——**如果这个 catch 被执行了，用户/运维/开发者怎么知道？** 答案不能是「看代码」——答案应该是一条可检索的信号。如果 catch 块里没有 `warnings.push`、`console.error`、`metrics.counter.inc()` 其中至少一项，那它不是容错——它是一个用 try/catch 写的注释。

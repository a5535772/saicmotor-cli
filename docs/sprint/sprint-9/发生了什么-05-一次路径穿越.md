## 认识这个 bug：三行路径拼出来的`../`

看 `findScript` 在改造前的核心路径构造逻辑——它是 CLI 引擎根据三层目录（service、resource、method）找到实际脚本文件的核心函数，约 50 行，但所有路径安全相关的代码就只有这 4 个候选：

```ts
// 候选路线 1：SAICMOTOR_SCRIPTS 环境变量覆盖
const override = firstExisting([
  path.join(process.env.SAICMOTOR_SCRIPTS, `${rel}.js`),
  path.join(process.env.SAICMOTOR_SCRIPTS, `${rel}.ts`),
]);

// 候选路线 2：插件 scripts 目录
const pluginScript = firstExisting([
  path.join(plugin.rootDir, plugin.manifest.scripts, `${rel}.js`),
  path.join(plugin.rootDir, "dist", plugin.manifest.scripts, `${rel}.js`),
]);

// 候选路线 3：编译产物 dist/scripts/
const compiled = path.join(distRoot(), "scripts", `${rel}.js`);

// 候选路线 4：源码树 scripts/
const source = packageFile(path.join("scripts", `${rel}.ts`));
```

`rel` 来自 `path.join(serviceName, resourceName, methodName)` —— 这里的三个参数来自 catalog 中 service 的 `name`、resource 的 key 和 method 的 `id`。`findScript` 本身没有验证这三个参数是否合法。

现在问一个问题：如果有一个 service name 是 `..`，resource 是 `evil`，method 是 `submit`，会发生什么？

`rel = path.join("..", "evil", "submit")` → `../evil/submit`

把这个 `rel` 带上第 3 条路线充当最后一个候选：`distRoot/scripts/../evil/submit.js` = `distRoot/evil/submit.js`。这已经在 `distRoot()` 外面了。如果攻击者能在预期的文件系统位置新建一个 `evil/submit.js`（比如通过插件目录布局构造），`fs.existsSync` 会返回 `true`，引擎会 `import()` 它并执行——到此为止就是一个完整的**任意脚本执行**。

## 原理：路径标准化不是安全边界

`path.join(TARGET_DIR, userInput)` 本身不提供任何安全测量——`path.join` 只是机械式字符串拼接加分隔符标准化，它不会拒绝前缀为 `..` 的输入。

**真正的问题是「信任输入的来源」——三个路径段来自 catalog，catalog 来自受控的 JSON 文件**——但受控不意味着其他代码可以读取和信任这份文件。防御应该在这里生效，而不是在「受控」上。

安全领域有一个术语叫「路径遍历」（也被 OWASP 称呼为 path traversal）：当一个攻击者能通过注入 `../` 来控制文件系统的路径解析，就可以访问到超出预期范围的文件。修复它只有一个模式：**先算目标文件，再问它还在不在允许区域内**。

## 代码改造

### 围栏 helper：先解析绝对路径，再把相对关系展开确认「没越界」

```ts
function within(base: string, candidate: string): boolean {
  const rel = path.relative(path.resolve(base), path.resolve(candidate));
  return rel !== "" && !rel.startsWith("..") && !path.isAbsolute(rel);
}
```

拆开来看每一步：

1. `path.resolve(base)` / `path.resolve(candidate)` —— 先把两个路径都解析成绝对路径，消除所有 `..` / `.` 成分。
2. `path.relative(resolvedBase, resolvedCandidate)` —— 计算目标路径相对基础路径的相对关系。
3. 检查这个相对关系：`rel !== ""`（不是空——即目标不能就是基础路径本身）、`!rel.startsWith("..")`（没有向上走）、`!path.isAbsolute(rel)`（没有跳盘符/根目录）。

如果这个函数返回 `false`——候选路径「不在基础路径内」——该路径就不是可以安全 import 的对象了。

### 落地：四条路线每一条都上了 `within` 门

```ts
// 候选路线 1：SAICMOTOR_SCRIPTS 显式覆盖
const candidates = [path.join(base, `${rel}.js`), path.join(base, `${rel}.ts`)]
  .filter((candidate) => within(base, candidate));
const override = firstExisting(candidates);

// 候选路线 2：插件 scripts + dist/plugin-scripts
const candidates = bases
  .map((base) => path.join(base, `${rel}.js`))
  .filter((candidate, index) => within(bases[index], candidate));
const pluginScript = firstExisting(candidates);

// 候选路线 3：编译产物 dist/scripts
const compiled = path.join(compiledBase, `${rel}.js`);
if (within(compiledBase, compiled) && fs.existsSync(compiled)) return compiled;

// 候选路线 4：源码树 scripts
const source = path.join(sourceBase, `${rel}.ts`);
return within(sourceBase, source) && fs.existsSync(source) ? source : null;
```

每个候选路径都必须通过 `within(baseDir, candidate)` 检测。如果 `rel` 含 `..` 走出基础目录范围，`within` 返回 `false`，`findScript` 直接跳过它并继续下一个候选——最终所有候选都不过线，返回 `null`——引擎不执行任何脚本。

## 这一讲的核心知识点

**`path.join(dir, userInput)` 不提供安全测量——每次拼接外部贡献的路径元素后应该做一次区间核实。** 路径标准化函数（`resolve`、`join`、`normalize`）只处理字符串表达层面的差异，不管访问权限或预期范围。权限检查必须由验证函数自己完成——是的，这会有性能成本，但衡量「成本」与「风险」时请记住：这里的安全性由最脆弱的一处输入控制，包内其他输入或外部文件均不在您的控制范围内。

**第一关防御是「信任输入」的边界——而不是输入内容的规范性。** 在这个例子中，来自 JSON catalog 文件名只是间接信任——实际上这些文件并不是系统自带的，它们是环境和插件安装的副产品。谁写入的？单靠文件名不要依赖权限约束回答这个问题。

**最后一点：这种攻击并不需要能越权新建文件。** 攻击者只需要知道有一个路径能让现有的其他文件中某处的脚本被 `import()` 执行——他们能操作的只是输入路径字符串本身。这种攻击无需文件系统访问。

# 发生了什么 · 第六讲：没说清谁生效——当警告信息不包含决策依据

> **修复编号：L4** | **严重度：🟡** | **改前分支：master@453a827**

---

## 认识这个 bug

想象这样的场景：你同时装了 `@saicmotor/plugin-alpha` 和 `@saicmotor/plugin-beta`——两个插件声明了同名的 service（比如都叫 `leave`）。CLI 必须做决定：选一个，警告说冲突了。

改造前的警告是这样说的：

```
service "leave" 冲突：@saicmotor/plugin-beta 与 @saicmotor/plugin-alpha 均提供，请用 plugin disable 处理
```

这条信息表面上提供了「正确」的事实——确实冲突了——但对用户来说有三件事空着：

1. **谁赢了？** 既然冲突了但 CLI 仍然继续运行——显然它选了一个 winner。但到底是 alpha 还是 beta？警告没说。用户必须自己去猜，或者做实验：`plugin disable plugin-alpha` → 再跑一次看效果。

2. **我该 disable 谁？** "请用 plugin disable 处理"是六个字，没有名字。"disable 哪个？"——用户必须从"连哪个生效都不知道"的事实里反推。

3. **语法是什么？** 命令叫 `plugin disable`，虽然用户很可能猜出要加插件名，但不清晰的"请用 X 处理"跟可执行的技术指示差别很大。

## 原理：报错信息的可操作性

一条好的工程师报错信息不只是描述事实——它必须让读者有 **可执行的路径走到修复**。三要素：

| 要素 | 含义 | 本例缺失？ |
|------|------|-----------|
| **身份** | 涉及谁（哪个模块/组件/文件） | ✅ 有（alpha 和 beta） |
| **结果** | 现在系统做了什么决定 | ❌ 没说谁生效 |
| **行动** | 如果这不是你想要的，你该怎么改 | ❌ 只说了 disable，没说 disable 谁 |

中间那列一旦缺失——用户不知道「现在谁生效」——ta 脑中的操作变成了：

> "要不我 trial-and-error 一下，disable 一个看效果？"

每一次 trial-and-error 都是一次系统交互的摩擦——命令要敲、配置要读、状态要恢复。在复杂工具里这可能是在浪费 10–30 秒，但对于偶尔使用的操作员可能是 5–10 分钟。

## 代码改造

只改一行。对比：

```diff
- warnings.push(
-   `service "${svc.name}" 冲突：${manifest.name} 与 ${existing.manifest.name} 均提供，请用 plugin disable 处理`,
- );
+ warnings.push(
+   `service "${svc.name}" 冲突：${manifest.name} 与 ${existing.manifest.name} 均提供。当前 ${existing.manifest.name} 生效；若要 ${manifest.name} 生效请先 plugin disable ${existing.manifest.name}`,
+ );
```

注意变量顺序：

- `existing` 是先加载的插件（已被 `loaded.push()` 推入）——是 winner。
- `manifest` 是后加载的插件——冲突检测时发生失控对象，是 loser。
- 第一版只说「均提供，请用 disable」，新版本说「X 当前生效，你要让 Y 生效的话先 disable X」。

测试也做了对齐（加强了语义断言）：

```ts
// 原来的弱断言
expect(conflictWarning).toContain("冲突");

// 现在追加的强断言——确认 winner=alpha 这件事被钉死在文案里
expect(conflictWarning).toContain("当前 @saicmotor/plugin-alpha 生效");
expect(conflictWarning).toContain("disable");
```

## 这一讲的核心知识点

**报错信息不是日志行——它是决策文档。** 一条报错信息应该告诉用户两件事：系统做了什么决定，以及如果用户想要不同的结果该怎么改。给出 `disable` 命令而不给目标对象，等于给了一个不知道往哪开的建议。

> 「身份」+「结果」+「行动」三缺二时，报错是另一个 bug：它说系统发现了问题，但不告诉你系统打算怎么走，也不告诉你怎么推翻它的决定。

对于工具型 CLI 尤其关键：用户可能上一次使用是两周前，对插件的加载顺序已经毫无记忆。当时的报错信息就是ta们唯一的诊断线索。

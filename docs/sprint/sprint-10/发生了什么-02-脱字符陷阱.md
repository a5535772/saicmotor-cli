# 发生了什么 · 第二讲：^ 的 semver 陷阱——每次 CLI 小版本升级都是对插件的 breaking change

> **Sprint 10 — 修复 2/4 | 改前分支：master@f8f20b0**

---

## 认识这个 bug

插件 `@saicmotor/plugin-leave` 的 manifest 里有一行：

```json
{
  "name": "@saicmotor/plugin-leave",
  "engine": "^0.8.0"
}
```

CLI 启动时会执行这行校验（在 `loader.ts` 中）：

```ts
if (!semver.satisfies(CORE_VERSION, manifest.engine)) {
  warnings.push(`插件 ${manifest.name} 与当前核心版本不兼容...`);
  continue;  // ← 跳过这个插件，不加载
}
```

这行逻辑本身没问题——CLI 应该拒绝兼容范围外的插件。问题在于 `"^0.8.0"` 在 semver 规范下的实际含义。

**semver 规范明确写了一条特殊规则：**

> `^0.x.y` = `>=0.x.y <0.(x+1).0`

翻译成人话：**`^0.8.0` 允许 0.8.x 的补丁版本升级，但不允许 0.9.0。**

验证一下：

```
semver.satisfies("0.8.1", "^0.8.0") → true   ← 补丁升级，OK
semver.satisfies("0.8.5", "^0.8.0") → true   ← 补丁升级，OK
semver.satisfies("0.9.0", "^0.8.0") → false  ← 小版本升级，被拒绝
```

这意味着：**CLI 的每一次小版本号提升（0.8→0.9→0.10…）都是对所有已安装插件的 breaking change。** 用户升级 CLI 之后插件被全部注册为不兼容并被静默禁用——业务命令全部消失。这不是性能回归——是功能塌缩。

而 CLI 恰好还在 0.x 阶段——而 npm 生态中大多数成熟项目在 0.x 阶段停留数月甚至数年。

## 原理：semver 规范的 0.x 特例

semver 2.0.0 规范（https://semver.org/）第 4 条：

> Major version zero (0.y.z) is for initial development. Anything MAY change at any time. The public API SHOULD NOT be considered stable.

规范把 0.x 阶段定义为**不稳定期**——API 可能随时变化，不承诺向后兼容。因此 `^` 符号在 0.x 阶段的行为是严格限制的：`^0.x.y` 只允许 `>=0.x.y <0.(x+1).0`——补丁升级可以，小版本不跨。

这个规则在 **稳定版（≥1.0.0）阶段是合理的**：`^1.2.3` 允许 `>=1.2.3 <2.0.0`——次版本和补丁版本的升级都可以。这是 semver 生态的标准做法。

但对于**一个 0.x 阶段的插件系统**，这个规则制造了一个矛盾：

- CLI 侧：0.8→0.9 是一个正常的 sprint 迭代——加了新功能、修了 bug、优化了性能。API 没有 breaking change。
- 插件侧：`engine: "^0.8.0"` 声明了"我只能在 0.8.x 上运行"——因为 semver 的 `^` 在 0.x 阶段就是这样定义的。
- 结果：一个没有 breaking change 的升级 → 所有插件被禁用。

**矛盾的核心不在代码里——在 semver 规范的 0.x 语义和实际开发节奏的不匹配上。**

## 代码改造

**改的不是 runtime 校验逻辑——改的是脚手架生成的内容。** `loader.ts` 的 `semver.satisfies` 校验不变——它仍然正确拒绝不兼容的插件。变的是**新生成插件的默认声明**——从 `^` 换成 `>=`。

### Step 1：脚手架模板用 `>=` 替代 `^`

```diff
// tooling-cmds.ts — init 命令生成的 saicmotor.plugin.json
- engine: "^0.8.0",
+ engine: `>=${CORE_VERSION}`,

// tooling-cmds.ts — init 命令生成的 package.json
- "@saicmotor/sdk": "^0.8.0",
+ "@saicmotor/sdk": `>=${CORE_VERSION}`,
```

`CORE_VERSION` 来自 `getCoreVersion()`——如前一篇所述，这是从 `packages/cli/package.json` 动态读取的。

### Step 2：`^` 和 `>=` 的兼容性对比

| CLI 版本 | engine 声明 | 0.8→0.9 兼容？ | 0.9→0.10 兼容？ |
|----------|-----------|:---:|:---:|
| 改造前 | `^0.8.0` | ❌ | ❌ |
| 改造后 | `>=0.8.0` | ✅ | ✅ |

`>=0.8.0` 的含义：任何大于等于 0.8.0 的版本都可以——包括 0.9.0、0.10.0、甚至未来的 1.0.0。在 0.x 不稳定期，这是唯一不制造虚假不兼容的声明方式。

### Step 3：现有插件不碰

`packages/plugin-leave/saicmotor.plugin.json`：
```json
"engine": "^0.8.0"
```

不改。它不是脚手架生成的——它是一个已发布的插件的 manifest。改它就是改历史——而且 `"^0.8.0"` 在 CLI 版本为 0.8.0 的环境下工作正常。

0.9.0 发布时，这些旧插件的 engine 声明会失效——届时有两个选择：手动升级它们的 engine 声明，或者在运行时校验里加一个过渡逻辑。那是 0.9.0 的决策——本次 sprint 只负责以后不再产生新陷阱。

### Step 4：`@saicmotor/sdk` 的 devDependency 同步处理

插件的 `package.json` 里依赖 `@saicmotor/sdk` 也是 `^0.8.0`——同样的 semver 陷阱会出现在 `npm install` 时：`"@saicmotor/sdk": "^0.8.0"` 不会拉取 `0.9.0` 的 SDK。所以 devDependency 也同步改成 `>=`。

## 这一讲的核心知识点

**读你所依赖的规范的原文——不要假设你知道一个符号的意思。** `^` 在 semver 中是"兼容的版本"——但"兼容"的定义在 0.x 和 ≥1.0 时完全不同。你如果只记住"`^` 允许小版本升级"，你会认为 `^0.8.0` 包含了 0.9.0。但实际上不包含——而这个差异写在 semver.org 的第 4 条，只是大多数人没读原文。

**semver 的 0.x 阶段和 `^` 的组合，对插件系统是结构性不利因素。** 0.x 阶段的设计意图是"快速迭代、不稳定 API"——但实际开发节奏是"小版本 = 常规 sprint、没有 breaking change"。`^` 的 0.x 行为在这种节奏下制造了虚假的不兼容——用 `>=` 替代是承认"我们的 0.x 小版本之间确实是兼容的"。

**最后一点：这个修复不是"性能优化"——它是用户在升级 CLI 后是否还能使用插件的决定性因素。**

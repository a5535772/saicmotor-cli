# 发生了什么 · 第一讲：四处硬编码的版本号——把"发版时别忘了改"从 checklist 里删掉

> **Sprint 10 — 修复 1/4 | 改前分支：master@f8f20b0**

---

## 认识这个 bug

打开 `packages/cli/src/cli/index.ts` 第 16 行：

```ts
program.name("saicmotor").description("面向 AI Agent 的企业 CLI 工具平台...").version("0.8.0");
```

打开 `packages/cli/src/plugin/suite.ts` 第 26 行：

```ts
"version: 0.8.0",
```

打开 `packages/cli/src/cli/tooling-cmds.ts` 第 47 行和第 85 行：

```ts
"@saicmotor/sdk": "^0.8.0",    // 第 47 行——脚手架生成的 package.json 模板
engine: "^0.8.0",              // 第 85 行——脚手架生成的 saicmotor.plugin.json 模板
```

打开 `packages/cli/src/plugin/loader.ts` 第 62-72 行：

```ts
function readCoreVersion(): string {
  try {
    const pkg = JSON.parse(readFileSync(resolve(findPackageRoot(), "package.json"), "utf-8"));
    return pkg.version ?? "0.0.0";
  } catch {
    return "0.0.0";
  }
}
const CORE_VERSION = readCoreVersion();
```

注意这里的一个关键不对称：**`loader.ts` 已经知道要动态读取版本号**——它有自己的 `readCoreVersion()` 从 CLI 的 `package.json` 读 `version` 字段。但另外三个消费者（`index.ts`、`suite.ts`、`tooling-cmds.ts`）仍然用着自己手写的 `"0.8.0"` 字符串。

`readCoreVersion()` 的逻辑是对的——但它被锁在了 `loader.ts` 里，没有被导出。其他文件如果要读版本号，有两个选择：复制粘贴这个函数（重复代码），或者继续硬编码（不一致的 bug 源）。

**6 处版本号、1 个动态读取函数被私有化、0 个导出**——这就是现状。每次发新版：

- 开发者改 `package.json` → `version`
- 开发者手动改 `index.ts:16` 的 `"0.8.0"`
- 开发者手动改 `suite.ts:26` 的 `"0.8.0"`
- 开发者手动改 `tooling-cmds.ts` 的两处 `"^0.8.0"`
- 测试里还有约 20 处硬编码——通常不被当作发版任务的一部分

这不是"麻烦"——这是**系统性不可靠**。漏改一处，`saicmotor --version` 和实际版本号不一致，用户以为自己装的是 0.9.0 但 CLI 打印 0.8.0；或者脚手架生成的插件声明了错误的 engine 版本。

## 原理：单一真相源（SSOT — Single Source of Truth）

这是整个 Sprint 9 第一讲就讲过的原则——在这里换一个角度重述：

> 系统中每一个事实应该有且仅有一个权威定义。其他节点只能引用它，不能复制它。

版本号是一个事实。`packages/cli/package.json` → `version` 是它的天然来源——npm 生态里版本号的权威记录本来就是 `package.json`。任何其他文件如果也写了 `"0.8.0"`，它就是在**复制事实**——并且承担了一个义务：在事实改变时保持同步。这个义务的违约概率不是 0%——随着时间的推移和新人的加入，它会趋向 100%。

## 代码改造

### Step 1：把 `readCoreVersion()` 提出去，变成公共 API

新文件 `packages/cli/src/version.ts`：

```ts
import { readFileSync, existsSync } from "fs";
import { resolve, dirname } from "path";

let cached: string | null = null;

function findPackageJson(dir: string): string | null {
  const candidate1 = resolve(dir, "..", "package.json");       // vitest/src: src/../ → packages/cli/
  if (existsSync(candidate1)) return candidate1;
  const candidate2 = resolve(dir, "..", "..", "package.json"); // dist: dist/src/../../ → packages/cli/
  if (existsSync(candidate2)) return candidate2;
  return null;
}

export function getCoreVersion(): string {
  if (cached !== null) return cached;
  const pkgPath = findPackageJson(__dirname);
  if (!pkgPath) { cached = "0.0.0"; return cached; }
  try {
    const pkg = JSON.parse(readFileSync(pkgPath, "utf-8")) as { version?: string };
    cached = pkg.version ?? "0.0.0";
  } catch {
    cached = "0.0.0";
  }
  return cached;
}
```

两个设计点：

1. **缓存。** 版本号不会在进程运行中途改变。第一次调用读文件，后续调用直接返回缓存值——`program.version(getCoreVersion())` 和 `SUITE_VERSION` 都不会引入重复 I/O。

2. **双路径查找。** `__dirname` 在 vitest 的源码模式是 `packages/cli/src/`，在 tsc 编译后是 `packages/cli/dist/src/`。前者 package.json 在 `../`（往上 1 层），后者在 `../../`（往上 2 层）。`existsSync` 两候选按序尝试，哪个存在用哪个——没有假设运行环境。

### Step 2：4 个消费者全部改引用

```diff
// loader.ts — 删掉私有 readCoreVersion，改为 import
- function readCoreVersion(): string { ... }
- const CORE_VERSION = readCoreVersion();
+ import { getCoreVersion } from "../version";
+ const CORE_VERSION = getCoreVersion();

// index.ts
- .version("0.8.0");
+ import { getCoreVersion } from "../version";
+ .version(getCoreVersion());

// suite.ts
- "version: 0.8.0",
+ import { getCoreVersion } from "../version";
+ const SUITE_VERSION = getCoreVersion();
+ // ... 在 generateSuiteSkill 内：
+ `version: ${SUITE_VERSION}`,

// tooling-cmds.ts
- "@saicmotor/sdk": "^0.8.0",
- engine: "^0.8.0",
+ import { getCoreVersion } from "../version";
+ const CORE_VERSION = getCoreVersion();
+ `>=${CORE_VERSION}`,
+ `>=${CORE_VERSION}`,
```

注意 `tooling-cmds.ts` 不只是去硬编码——它还做了 `^ → >=` 的转换，这属于下一讲的主题。

## 这一讲的核心知识点

**任何需要"发版时别忘了改"的东西都是 bug——不是提醒。** 一个值如果散落在 N 个文件中，手动同步的可靠性是 `1/N` 的 N 次方——人类不擅长机械的逐行对比。单一真相源不是"最佳实践"，是对人类错误率的工程补偿。

**提取公共函数时，考虑运行的物理环境。** `__dirname` 在开发模式（tsx/vitest）和生产模式（tsc 编译后）下指向不同的位置。一个不接受环境假设的 `findPackageJson` 比一个路径常量的 `resolve(__dirname, "..", "package.json")` 更鲁棒——多一层逻辑换来不依赖运行方式的确定性。

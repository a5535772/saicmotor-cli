# 发生了什么 · 第四讲：测试里的魔术字符串——当 `"0.8.0"` 在 5 个文件里出现了 20 次

> **Sprint 10 — 修复 4/4 | 改前分支：master@f8f20b0**

---

## 认识这个 bug

`grep -rn "0\.8\.0" packages/` 在改造前输出约 30 行。挑出源文件（不算 `node_modules`），分布如下：

| 文件 | 出现次数 | 类别 |
|------|:---:|------|
| `packages/cli/package.json` | 1 | **真相源**（不改） |
| `packages/sdk/package.json` | 1 | 同步目标（sync 脚本负责） |
| `packages/cli/src/cli/index.ts` | 1 | 硬编码（已由前两讲消除） |
| `packages/cli/src/plugin/suite.ts` | 1 | 硬编码（已由前两讲消除） |
| `packages/cli/src/cli/tooling-cmds.ts` | 2 | 硬编码（已由前两讲消除） |
| `packages/plugin-*/saicmotor.plugin.json` | 3 | 已有插件 manifest（不动） |
| `packages/cli/test/unit/tooling-cmds.test.ts` | ~6 | **测试硬编码（本期主题）** |
| `packages/cli/test/unit/plugin-cmds.test.ts` | ~8 | **测试硬编码（本期主题）** |
| `packages/cli/test/unit/plugin-registrar.test.ts` | ~2 | **测试硬编码（本期主题）** |
| `packages/cli/test/unit/script.test.ts` | ~2 | **测试硬编码（本期主题）** |
| `packages/cli/test/unit/state.test.ts` | ~4 | **测试硬编码（本期主题）** |

源文件的硬编码已经在前两讲改完。但测试文件里还有 20+ 处 `"0.8.0"` 字面量——分布在 5 个文件的测试 fixture 和断言语句中。

当 CLI 从 0.8.0 升级到 0.9.0 时，这些测试会失败吗？大部分不会——它们测试的是逻辑（"版本号生成正确"、"engine 字段存在"、"插件列表返回版本号"），而不是"版本号等于 0.8.0"。但如果用了 `toBe("0.8.0")` 这种精确断言（如 `plugin-cmds.test.ts:247`），版本号一改就红。

更重要的是：**即使测试不红，测试的内聚力被破坏。** 一个读测试的人看到 `version: "0.8.0"` 会认为 0.8.0 是测试逻辑的核心——而事实是版本号可以是任何值，测试不依赖它是 0.8.0。

## 原理：测试中的魔术常量与 fixture 语义

测试代码中硬编码的值分三类——每类需要不同的处理：

| 类别 | 例子 | 含义 | 处理 |
|------|------|------|------|
| **断言值** | `expect(manifest.version).toBe("0.8.0")` | "版本号应该是当前 CLI 的版本" | 改动态 `getCoreVersion()` |
| **真实 fixture** | `{ name: "plugin-leave", engine: "^0.8.0" }` | 模拟**已有插件**的 manifest——engine 用旧 `^` 格式 | 保留 `^` 格式，但值从动态获取 |
| **脚手架输出** | `expect(manifest.engine).toBe("^0.8.0")` | 断言新生成插件的 engine 格式 | 改 `>=` 格式 + 动态值 |
| **输入无关值** | `{ engine: "^0.8.0" }` 作为校验输入 | 任何能通过引擎校验的字符串都行——测试不关心具体值 | 保留 `^0.8.0` 或改为其他固定值 |

这其中关键的是第二类：**真实 fixture**。在 `plugin-cmds.test.ts` 里，测试构造了一个模拟的"已安装插件"：

```ts
fs.writeFileSync(
  path.join(pkgDir, "saicmotor.plugin.json"),
  JSON.stringify({
    name: "@saicmotor/plugin-leave",
    engine: "^0.8.0",         // ← 这是历史事实——真实插件就这样声明的
    skills: ["skills/saicmotor-leave"],
  })
);
```

这里的 `"^0.8.0"` 不是任意值——它是真实已发布插件的 engine 声明的复制品。改它变成 `">=0.8.0"` 会让测试测试一个不现实的状态——没有插件用过 `>=` 格式的 engine 声明。这个 fixture 需要**语义保留**——`^` 格式不变，但具体的版本号从动态读取。

## 代码改造

### 模式一：断言值 → `getCoreVersion()`

```diff
// plugin-cmds.test.ts:247
- expect(result.data!.version).toBe("0.8.0");
+ expect(result.data!.version).toBe(getCoreVersion());
```

```diff
// state.test.ts:41
- expect(reloaded.plugins["@saicmotor/plugin-leave"].version).toBe("0.8.0");
+ expect(reloaded.plugins["@saicmotor/plugin-leave"].version).toBe(getCoreVersion());
```

### 模式二：真实 fixture（保留 `^` 前缀 + 动态版本号）

```diff
// plugin-cmds.test.ts
- engine: "^0.8.0",
+ import { getCoreVersion } from "../../src/version";
+ engine: `^${getCoreVersion()}`,
```

```diff
// plugin-registrar.test.ts
- version: "0.8.0",
+ version: getCoreVersion(),
```

### 模式三：脚手架输出 → `>=` + 动态值

```diff
// tooling-cmds.test.ts:85
- expect(manifest.engine).toBe("^0.8.0");
+ expect(manifest.engine).toBe(`>=${getCoreVersion()}`);
```

### 模式四：输入无关值 → 保留不动

```diff
// tooling-cmds.test.ts:135, 161, 171, 203
// 这些是传入校验函数的输入——任何合法 engine 字符串都行
  engine: "^0.8.0",   // ← 不改——测试不依赖它是 0.8.0，只是 fixture 填充
```

### 不改的：`"0.9.0"` 升级场景

`plugin-cmds.test.ts` 第 371 和 391 行有 `"0.9.0"` 硬编码——这是测试**升级场景**的 fixture（"当前是 0.8.0，升级到 0.9.0 后会怎样"）。它不是当前版本号——是固定的测试输入。不动。

## 这一讲的核心知识点

**测试中的魔术字符串分四类——不要一刀切。** 有些是"应该等于真相源的值"（用动态读取）、有些是"模拟历史事实的 fixture"（保留格式、动态取值）、有些是"任意合法值"（不改）、有些是"模拟未来状态的固定值"（不改）。一刀切改成全部动态读取会让升级场景测试失去参考系。

**测试不红 ≠ 内聚力在线。** `version: "0.8.0"` 的硬编码在测试中不会因为版本号升级而失败——但阅读者必须推断"这是 0.8.0 特定的测试吗？"这类额外判断。让测试只用源文件已经建立的符号（如 `getCoreVersion()`），就是让测试的内聚力与源文件的内聚力耦合——源文件改了，测试自动跟。

**"保留 fixture 中的 `^`"是对历史事实的测试。** 已有插件的 `engine: "^0.8.0"` 是一个真实发生过的事情——它测试的是"引擎校验逻辑是否正确处理 `^` 声明"。如果你把 fixture 的 `^` 也改成了 `>=`，你就不再测试这个历史路径——而它是未来版本号升级时最关键的测试路径。
